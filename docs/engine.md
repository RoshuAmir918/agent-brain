# Agent Brain engine

Agent Brain is an installable Python package for the arithmetic half of remembering. Vaults contain notes, not a vendored engine. The judgment half lives in the vault's Memory Spec and routine skills.

Git is the ledger. Each nightly stage is one commit, so `git log --grep` says whether a stage ran, the first missing commit is where a resume continues, and `git revert` undoes a stage. A local commit can remain unpushed; a clean working tree only proves there are no local changes.

## Installation and updates

Python 3.11 or newer is required. From a source checkout:

```sh
python3 -m pip install .
# For development, including tests:
python3 -m pip install -e '.[test]'
brain --help
```

Install a built wheel on another machine with `python3 -m pip install /path/to/agent_brain-0.1.0-py3-none-any.whl`. When releases are available on your package index, use `python3 -m pip install -U agent-brain`; no index publication is implied by this checkout. An updated source checkout can instead be installed with `python3 -m pip install -U /path/to/agent-brain`.

Run these from the vault repository after installation or an upgrade:

```sh
brain install-skills
brain responsibility "<Name>" --skill <name> [--records <folder>]
brain install-scripts
brain install-provider
```

`install-skills` renders the routines into `<vault>/<hermes_dir>/skills/<skill_prefix><routine>/SKILL.md` and prints the absolute directory to put in Hermes `skills.external_dirs`. The core routines (attribute, sleep1, sleep2, rem, recall, improve, people, explore, watch) are overwritten on every run so package updates reach them, except for a `## Local` section at the end of the rendered file, which is carried over verbatim: the vault's own additions live there. The day routines (morning, midday, evening) are written only when absent, so local edits survive. `brain install-skills --force` resets the day routines to the package versions. Templates are shipped in the wheel; edits to rendered copies are overwritten. Rendering uses literal token replacement, not Python format strings. `install-scripts` copies the packaged shell scripts to `$HERMES_HOME/scripts` (default `~/.hermes/scripts`), makes them executable and prints the installed paths. `install-provider` atomically replaces the three packaged memory-provider files in `$HERMES_HOME/plugins/brain` (default `~/.hermes/plugins/brain`) and prints setup instructions. None of these commands edits global config or schedules jobs.

Set `VAULT_REPO` for cron to the repository root (default `$HOME/brain`), and `HERMES_HOME` if it is not `~/.hermes`. Ensure `brain` and `hermes` are on the cron PATH. `refresh.sh` pulls the notes, compiles context, renders skills and copies the configured SOUL into the Hermes home. `export-sessions.sh` exports sessions (conversations into the vault, the agent's own routine and evaluation sessions and every JSONL shard into `$HERMES_HOME/records/sessions/`, so each profile on a shared machine keeps its own), builds yesterday's digest, and invokes refresh. These retain the existing commit/push behavior: executing them is a publishing operation, unlike the install commands. No script is run by installation.

## Configuration

Place `brain.toml` at the vault repository root. All keys are optional and merge with these defaults:

```toml
[brain]
vault = "memory"
agent_dir = "agent"
people_dir = "people"
agents_dir = "agents"
human_profile = "human/Profile.md"
sources_dir = "sources"
hermes_dir = "hermes"
human_name = "Human"
agent_name = "Agent"
owner_user_ids = []
maintainers = []
log_dirs = []
skill_prefix = "brain-"
update_source = "git+https://github.com/RoshuAmir918/agent-brain"   # "" disables auto-update
```

`vault` and `sources_dir` are relative to the repository root. The agent, people, agents, human profile and Hermes paths are relative to the vault. `sources_dir` remains read-only. `Archive/` is a supported read-only sibling link namespace; it is not a new config key. Layout paths must be relative without `..`. Tasks, Triggers, CURRENT and the other note basenames remain fixed. Generated wikilinks use the configured `vault` prefix. `BRAIN_HUMAN_NAME` and `BRAIN_AGENT_NAME`, when set, override the configured display names, including rendered skills.

`timezone` is the owner's IANA zone, default `America/Los_Angeles`: the export script's "yesterday" (`brain timezone` prints it; `BRAIN_TZ` in the environment overrides), digest day boundaries and timestamps, and the default date of `health`, `audit` and `nightly`. A profile whose owner sleeps in another zone than the host must set it, or the 00:30 export lands on the wrong day.

`BRAIN_TODAY=YYYY-MM-DD` in the environment pins the engine's today, for evaluations against throwaway vaults: every command that computes today or an age from it (`state`, `needs-you`, `loops`, `stale-tasks`, `nightly`, `digest`, `health`, `audit`, `session-context` and the provider's calls, the scripts' dates) uses it, and a ledger row or conversation capture without `--at` takes that date with the current time of day in the configured zone. An explicit `--date` or `--at` still wins. A value that is not a date fails every command.

An optional `[context]` table sets what enters an agent's context. Each key has an environment override, and the environment wins over `brain.toml`:

```toml
[context]
hot_words = 6000          # BRAIN_HOT_WORDS: the directory's active-note body-word budget and compile-context's warning
sections = ["before", "start", "current", "primed", "goals", "triggers", "upcoming", "tasks", "directory"]   # BRAIN_CONTEXT_SECTIONS, comma-separated
prefetch = true           # BRAIN_PREFETCH (0 or 1)
prefetch_limit = 6        # BRAIN_PREFETCH_LIMIT: notes recalled per message
prefetch_chars = 1500     # BRAIN_PREFETCH_CHARS: the recalled block's cap
prefetch_form = "names"   # BRAIN_PREFETCH_FORM: names, snippet or full
hot_threshold = 7         # BRAIN_HOT_THRESHOLD: days a single use stays hot
warm_threshold = 28       # BRAIN_WARM_THRESHOLD: days a single use stays warm
people = "card"           # BRAIN_PEOPLE: off, line or card; what prefetch adds for a person named in the owner's message
```

`sections` chooses which parts of `.hermes.md` load, never how each renders: `before` is the engine's Before-answering paragraph (look again at what is loaded before a plan, advice or a person; a parked task has no question; a reminder is a Triggers row), `start`, `current`, `primed`, `goals`, `triggers` and `tasks` are those notes' blocks (Primed and Goals are skipped until the vault has them), `upcoming` is the engine's scan of dates in the next seven days, `directory` starts with the most active notes and their index lines, followed by the names-only directory. The legacy section name `hot` is accepted as an alias for `directory`; the header and closing line always remain. `prefetch_form` `names` is the default block of paths and reasons, `snippet` replaces each reason with the note's index line, and `full` gives each note's body; both are cut to `prefetch_chars`. The thresholds also set `brain simulate`'s defaults. Unknown keys or sections, non-integers and unknown forms fail every command; the provider reads the prefetch keys itself from the vault's `brain.toml` and the Hermes environment, and logs an error and skips recall on an invalid one.

`owner_user_ids` is a list of strings, default `[]`, containing the owner's platform user IDs. An entry `platform:id` (for example `demiurge:k57...`, the permanent Demiurge id) matches only sessions on that platform; a bare entry matches any platform. Either the primary or alternative session ID can identify the owner; display names and chat IDs cannot. This key does not change skill template values.

`maintainers` is a list of platform user ids in the same form as `owner_user_ids`, default `[]`, for the humans or agents who keep this brain's machinery running without being its owner: whoever set it up, or an agent that runs a nightly briefing. A session from one of them gets the maintainer block, followed by the current `brain health` report. The block tells the agent to talk to a maintainer about its work as to a colleague on the same machine, in plain words ("we were setting up access to the X site for the owner and it keeps failing because of Y"), to hand over process records on request (`brain health`, `brain audit`, ledger lines, its skills, the cron table), and to do engine maintenance on request without the owner: `brain update`, `migrate-check`, pending migrations (a step that asks the owner a question is carried to the owner by messaging them, since the owner is never an outside party; a step that creates a routine is the engine's instruction, not a schedule change), skill, script and provider reinstalls, `validate`, `health`, `audit`, a restart of its own gateway, and committing and publishing the engine-state changes these produce. What it does not pass along is the owner's content: what they said, what their notes say, the people in the vault and their lives, credentials, transcripts, digests. The reason given is flow, not access: whatever the agent posts becomes part of the maintainer's memory and may reach whoever they talk to next. A maintainer holds the schedule of the engine's routines (night stages, export, refresh, improve, people, watch, explore, template day defaults) and the agent applies their create, move, pause, resume, remove or combine request in that session; the briefing hour and any routine the owner asked for by name stay with the owner. A maintainer cannot grant permissions or credentials, or edit notes. Add the key with the engine version that introduced it or later installed: older engines reject unknown `brain.toml` keys.

`log_dirs` is a list of folders under `agent_dir`, default `[]`, whose files are records rather than notes: receipts, ledgers, results. They join the engine's own ledgers (Explorations, Use Log, Sleep Log, Tasks Archive, Research) as kind `log`: never activated, never among the directory's most active notes, never link-checked. A note anywhere else can declare the same by putting `kind: log` in its frontmatter. Add a folder here as soon as the agent starts filing process artefacts in it, or they compete with knowledge for the hot budget.

The rule behind it: a routine owns three places, a state file it overwrites, a monthly ledger it appends one line to, and the notes it feeds knowledge into, never a file per run. Priming follows it: Sleep 2 overwrites `<agent_dir>/Primed.md` nightly; the older dated `Primed/` folder is still recognised and expired.

Routine ledgers live at `<agent_dir>/<Routine>/YYYY-MM.md`, with `kind: log`, `tier: cold` and five columns: `when | routine | outcome | account | next step`. `when` is a date or local date and time (`YYYY-MM-DD HH:MM`); outcome is `done`, `progress`, `waiting`, `blocked`, `failed` or `nothing`. Keep each entry under 25 words. Older four-column `when | routine | account | next step` rows still read, with no structured outcome.

`brain ledger append <routine> --outcome nothing --account "Nothing new." [--next "..."] [--at "YYYY-MM-DD HH:MM"] [--vault <path>]` appends in the configured timezone and prints the path. `--json` instead reads one object from stdin with `routine`, `outcome`, `account`, and optional `next` and `at`. The writer sanitises whitespace and pipes, finds a routine's folder from its existing rows (so `morning` can live in `Letters`), or creates `<Routine>` with its first letter upper-cased. Add a new folder to `log_dirs` yourself; the command never edits `brain.toml`.

`--skill <name>` instead of a routine names the cron job's skill; the engine maps it to the routine (a responsibility hub's `records`, else the skill without `skill_prefix`). The night stages (attribute, sleep1, rem, sleep2) are skipped: each is one commit, and git is their ledger.

**After the session.** The Hermes provider (`brain install-provider`) makes one bounded side call through the host's model after each session, asking for a structured record against a fixed JSON schema, retried once, falling back to the reply's first line. A cron run, when it ends, becomes one row in its routine's ledger through `brain ledger append --skill`; its schema and ledgers are unchanged. A conversation, once quiet for 90 seconds or ended, sends only its new turns through `brain journal append` to capture loops, closures, answered asks and ready relays, a needs-you question, access requests, Working together directions and Noted facts. `next` and `thought` remain in the schema for compatibility; the model is no longer asked for a thought. An outcome of `nothing` with no capture or open work writes nothing. Diary rows stopped in 0.25.0; old `<agent_dir>/Journal/YYYY-MM.md` files remain as history. Their format is `when | platform | outcome | headline | next step`, with optional indented `needs you`, `touched` and `thought` lines. `brain journal recent [--count 30]` still reads them, and `brain journal append --synthesis` still writes a catch-up from stdin. A `needsYou` becomes an ask in CURRENT; touched titles that do not resolve or would be withheld by the export are dropped. The record sees existing asks with their ids and up to 20 open loops. Its conversation-only `resolved` and `ready` arrays each hold at most five ids or exact texts: `resolved` removes asks answered or made moot here through `needs.resolve`, with the reason "answered in conversation"; `ready` marks owed loops whose answer the owner just gave, for watch to relay. Already gone asks or closed loops are harmless on a retry. Work the owner hands over for later ("look into…", "have something by morning") becomes a `promised` loop with its due time. Routines exclude these fields, as they do `loops` and `closed`.

**Loops.** `<agent_dir>/Loops.md` is a warm, unpinned orientation note, headed `# Loops`, with `## Open` and `## Closed`. The after-conversation writer adds `- YYYY-MM-DD HH:MM · promised|owed|waiting · <text> · [[source]]`, optionally followed by indented `with:`, `due:` and `ready: YYYY-MM-DD HH:MM` lines. Sources use the first public touched note, otherwise `Conversations`. Closed bullets carry `closed: YYYY-MM-DD HH:MM · done|dropped · <because>`; the latest 50 stay in Closed and older ones move to `Loops/YYYY-MM.md` logs by closing month. IDs are stable from kind and normalized text; repeated open text is ignored. `brain loops` lists open work; `--json` returns `open`, `due` and `closed_recent`. `--due` always exits 0; `--quiet` prints nothing and exits 1 when nothing is due, 0 otherwise. Add with `--add TEXT --kind K --source NOTE [--with WHO] [--due "YYYY-MM-DD HH:MM"]`; close with `--close ID_OR_TEXT --outcome done|dropped --because TEXT`. Explicit due dates become due at local midnight, or at their named time; without one, promises and owed answers become due after four hours. Waiting loops get at least 24 hours before attention, and a future due date still holds them back. `loops.ready(config, which, at)` makes any open loop due immediately, whatever its kind, age or deadline; it preserves the first ready time on retries. Watch works from `brain loops --due`; validate names open loops older than 14 days. The owner's state export includes `loops` (id, kind, text, with, due, ready, since, source) and `loopsClosed` (ten recent closures, with closed date, outcome and because), using the same source privacy boundary as Needs you. `journal` remains in the export for one more release.

The provider reaches the host's model through the same facade the host gives plugins; without one it records nothing. A recording keeps its original vault and platform, one recording runs at a time, and a failed call or write leaves the turns for the next attempt; after compression or `/resume` only new turns count. Every engine write to a shared file holds a per-vault lock under `~/.cache/brain`, outside the vault and independent of `TMPDIR`. Records can land after the agent's commit, so pulls use `--autostash`. A routine is recorded once when Hermes tears it down, with a model call bounded at 20 seconds; Hermes gives cron cleanup 10 seconds by default, so a row can land after the run, and a one-shot `hermes cron run` may exit first (raise `cron.cleanup_timeout_seconds` to 45 to keep it). A plugin in Hermes's isolated plugin host (`plugins.isolation: host`) cannot reach the model and records nothing.

`brain nightly --write` collapses two or more `nothing` rows per routine per past day into one: `2026-10-27 08:30–22:30 | watch | nothing | 14 runs, nothing new. | ...`. Counts and time ranges survive a later collapse. Other outcomes, legacy rows and today or future rows stay untouched; preview changes only its disposable copy. Engine logs with different schemas (Use Log, Sleep Log, Tasks Archive, Research, Explorations, Improvements, Retrieval Checks and Loops) are not routine ledgers.

Discovery walks upward from an explicit `--vault`, or from cwd when omitted, choosing the nearest `brain.toml`. Without `--vault`, the vault is `<config repo>/<vault>`. With it, the given path is the vault root, while the discovered config supplies its layout. Without any config, defaults apply; the repository root falls back to Git's top level, or the explicit vault's parent / cwd when outside Git. No identity or setup interview is required by the engine.

## Hermes memory provider

The packaged `brain` provider supplies context without requiring the agent to choose a retrieval tool. It reports itself available wherever the `brain` CLI runs and finds the vault per session: the session's working directory, then the profile's `terminal.cwd` (from the session's Hermes home, else `HERMES_HOME`), then `VAULT_REPO`, then `~/brain`, so one host process serving several profiles never sends a profile's sessions to another owner's vault; a session with none of those runs without the brain and logs a warning, so a missing setting is visible rather than silent. At initialization it runs `brain session-context` once and caches the resulting system-prompt block for that session. CLI sessions and either ID in `owner_user_ids` receive only an owner identification. When `<hermes_dir>/pending-migration.md` exists, the owner's sessions, a maintainer's and the agent's own cron runs (platform `cron`, no user) also receive a notice to perform it in that session, drafting anything the owner must answer rather than stopping, and to finish with `brain migrate-done`; a session with anyone else never does. A cron run otherwise receives nothing. A third party is matched in `<people_dir>/*/Profile.md` bodies, not frontmatter. First by a line qualified with the session's platform (``- **Demiurge:** `<id>` ``, `Demiurge: <id>`; label case-insensitive) whose value starts with either session ID; only when no profile has one, by whole-token IDs anywhere in the body, where an email local part does not count as a handle. A prose mention in another profile therefore cannot make a qualified match ambiguous. One match supplies the profile (at most 250 words, with an ellipsis when truncated and a full-path pointer), applicable person/group/anyone disclosure rows, and the default denial rule. Missing Disclosure.md is explicit. Oversized rule sets are not partially injected: the block requires opening Disclosure.md before any disclosure. Unknown and ambiguous identities receive the stranger warning; ambiguous matches are listed. Without platform or IDs, no block is injected. The session block stays around 400 words.

Demiurge's identity directory is cached outside the vault at `$HERMES_HOME/records/directory.json`. `brain people sync` reads `demiurge intellects --json` from stdin, or runs it with `--run` (also done by hourly refresh); it reconciles id-less profiles only through explicit handles of the right kind, never display names or existing ids. `brain people who <id-or-handle> [--json]` identifies a person or intellect and names any profile carrying their id. For an unmatched Demiurge sender, session context adds the directory identity before the existing stranger warning, granting nothing; matched profiles keep their existing behavior. The hygiene check in `brain validate` lists Demiurge ids shared by multiple people or intellect profiles so they can be merged.

Before each API call, `prefetch` retrieves for the current user message when it contains at least two non-stopword tokens. It calls `brain retrieve --json --limit 6` with at most 300 query characters, returning note paths, tiers and reasons in a block capped at 1500 characters; `[context]` sets the limit, the cap, the form and whether it runs at all. It returns no block for no candidates or failures. Every subprocess has a five-second timeout. The provider adds no tools, stores no turns, and performs no network availability checks.

`people` adds a pointer when the owner's message names someone with a profile under the people directory (whole word, full name or first name, case-insensitive), once per person per session and only in the owner's own sessions (the provider checks its cached session block; a friend asking about a friend never has that person's profile put in front of the model): `line` is one sentence per person from the first line of their profile with the folder path, `card` the profile cut to 150 words plus the newest history entry, `off` nothing. It is the `brain people-mentioned --form <form> -- <text>` command, run by the provider before recall.

An intellect registered under the agents directory is recognised from a platform-qualified id line on its profile (`- **Demiurge:** `<id>``), else any id line; its session block names it as an intellect, names its owner from the profile's `Owner:` line (a wikilink or a name), says its words are claims (and, for any known person, that a request which needs the owner is put to the owner now and the person told, never offered and left), resolves inline what its owner may learn (`brain access` for that owner; with no resolvable owner, nothing beyond what anyone may learn and an ask to the owner), and carries the relay rule: a request it relays for the owner is the owner's mail, put to the owner now (on Demiurge with `demiurge_tell_owner`, `text` when it should reach their phone; elsewhere an ask in Needs you), answered in the room with "asked", never acted on before they answer, never held for a briefing, and granting nothing. A stranger on Demiurge gets the same relay rule and the lookup rule first: `demiurge intellects` in the shell before treating the sender as a stranger, a profile from the template when it is one, and identity doubt is about a claim that contradicts the directory, not a sender the vault has not recorded.

Injected text is **never attribution credit**, including automatically injected profiles and disclosure rules. Only notes the agent subsequently opens on demand are eligible for observed attribution under the usual exclusions; loading pointers does not count as use. Disclosure text is guidance for the agent, not a retrieval access-control filter.

From the vault repository, with `brain` on the gateway's PATH:

```sh
brain install-provider
hermes config set memory.provider brain
```

Ask the owner for their permanent platform IDs and add `owner_user_ids = ["demiurge:<permanent id>"]` to the existing `[brain]` table, then restart the gateway. Verify with a non-owner Demiurge session or ask the agent what its provider block says. `brain paths provider` prints the installation directory. Hermes can use a different Python interpreter: the installed plugin imports no `brain` modules and uses only the standard library.

The plugin finds the repository from the session's `cwd`, then `VAULT_REPO`, then `$HOME/brain`, using the first location with a `brain.toml` (including parent directories). Each CLI subprocess runs with that repository as cwd so its configured vault layout applies. Set `HERMES_HOME` when installing into a non-default Hermes home. Installing or updating copies files only; enabling the provider and restarting remain explicit steps.

## Today for the owner

`<agent_dir>/Memory Spec.md` is the engine's description of how memory works, so `brain install-skills` re-renders it from `templates/memory-spec.md` with the skills, keeping the vault's frontmatter and its `## Local` section.

Two sections of `.hermes.md` carry the owner's day into every session. **Primed** (`<agent_dir>/Primed.md`, kind `primed`) is judgment: the prime routine overwrites it each morning, after the People review, with where the owner is and with whom, what they said they would do, the people with something happening this week, what is held and waiting for them, the notes likely to come up and at most one nudge. `compile-context` loads at most its first 300 words, cut at a line, and `brain validate` reports a longer one. It follows CURRENT, is never a retrieval candidate and never enters the directory's active block. Prime also runs `brain channels mail --since <last_run>`: its checkpoint is `last_run`, an ISO datetime in `$HERMES_HOME/records/prime/state.json`, defaulting to yesterday at 06:30 in the owner's zone. It opens only headers suggesting a person needs the owner today, a deadline, a booking or a change of plans; important facts go into the owning task as in watch, never copied message bodies. At most three one-line facts bearing on today enter Primed's Today part. After writing Primed and compiling context successfully, prime saves the run's start time as the next checkpoint. Morning receives new mail through Primed and does not search mail itself; its Today leads with the owner's location and calendar when those matter.

**Upcoming** is arithmetic: `compile-context` scans every hub, profile, register and person's History for a sentence naming a date in the next seven days (ISO or `November 2`; a bare month and day within the last 180 days is this year, otherwise next), skipping episodes, reflections, dreams, Primed, logs and the Journal, and lists up to twelve as `- Fri Oct 30 · <sentence> · [[note]]`; a date that is today is kept only when the sentence looks ahead (due, until, flight, visit, call). A short sentence leans on the one before it for its subject, and only its own dates count. The fix for a wrong line is the sentence in its note.

With a Demiurge sync, Upcoming also includes a sibling **Calendar: today and the next 7 days** block, capped independently at twelve compact events. It reads `$HERMES_HOME/channels/<account>/calendar/YYYY-MM-DD.md` for today through day seven, only for live `owner` registry rows, using the email in `identity`, otherwise the folder named in `reach`. Today's starts come first with times, then ongoing multi-day events marked `now, through <last day>`, then coming days. Events deduplicate by `id` across days and accounts; declined and cancelled events are skipped. Titles, times, a place/city shortened to sixty characters and the owner's response are shown. All-day ends are exclusive (a stay ending November 10 is ongoing through November 9); timed events carry local RFC3339 offsets in Demiurge's writer and are rendered in `brain.timezone`. The space-separated local time form is also accepted. Missing HERMES_HOME, folders or files add nothing; a vault works without Demiurge. The block is controlled by the existing `upcoming` context section and included in the context word count; note dates keep their existing independent cap and behavior.

Triggers load only the table of triggers still waiting to fire; the `## Fired` and `## Retired` sections are records, read from Triggers.md on demand.

Held work lives under `<agent_dir>/Prepared/`: things made or drafted for the owner that no task owns, kind `draft`, `tier: warm`, with an `index_line` and a wikilink from the note each serves. A draft gets its creation as its first use, is a retrieval candidate, is never auto-loaded, and goes cold on its own when never wanted. `brain state --json` lists drafts among outputs. The explore routine writes no row of its own: the engine records each run under `<agent_dir>/Explore/YYYY-MM.md` like any routine, and the skill asks that the account name the class (`inbound`, `work`, `people`, `occasion`) and the disposition (`filed`, `held`, `messaged`, `delivered`, `nothing`), which Sleep 2's weekly service pass reads. The older agent-written `Explorations/` ledger stays as a record.

## Goals

`<human_profile's folder>/Goals.md` is the owner's goals in their own words, four headings: Aspirations, Active goals, Adopted practices, Set aside. A goal enters Active goals only when the owner calls it one or returns to it on a second day; with no dated evidence for sixty days Sleep 2 nudges once through the briefing, and after thirty more days of silence moves it to Set aside, dated. It is an orientation note, compiled into `.hermes.md` after CURRENT when it exists, and skipped when the vault has none yet. The recall skill holds the rule: a lens for what the agent chooses to do and for advice it is asked for, never raised uninvited, never a reminder, a schedule or outward action; a goal does fund preparation, which the explore routine holds under `Prepared/` until it comes up. The improve routine proposes standing work toward goals nobody is working on. Skill templates can name it with `{human_goals}`.

## Responsibilities

Standing work with judgment in it is a responsibility with three linked homes: a hub note at the vault root whose frontmatter carries `skill:` (the own skill's folder name) and `records:` (a folder under `$HERMES_HOME/records/`), the skill itself under `<hermes_dir>/skills/`, and the records folder. `brain responsibility "<Name>" --skill <name> [--records <folder>]` renders the hub and skill from the packaged templates (`src/brain/templates/`), existing files untouched, and creates the records folder; `--records` defaults to the skill name without the prefix. `brain validate` reports an own skill (one the package did not render) that no hub names, a hub whose skill is missing, and a hub without a records folder; the nightly write does not gate on this, only the on-demand command reports it. It also reports a note whose frontmatter `kind` is undeclared; the declared kinds are `hub`, `profile`, `episode`, `reflection`, `task`, `trigger`, `log`, `dream`, `orientation`, `primed`, `draft`, `conversation` and `procedure`, and the Memory Spec lists the same. `<agent_dir>/Improvements/` is a ledger folder by default. The `improve` core routine studies one responsibility each morning and proposes new ones from the digest; the recall skill holds the rule that an own skill is edited only in the session where the owner adopts a proposal.

## Routines

Every routine is the engine's: `brain install-skills` re-renders each one hourly and keeps a vault's own steps under a `## Local` heading at its end. Morning and evening were the vault's until 0.18; their first render keeps the vault's copy beside the new one as `previous.md`, once, for the agent to move its own steps under Local. One job each: attribute, sleep1, rem and sleep2 at night (sleep2 repairs retrieval and writes weekly reflections), people, then prime (Primed), improve, morning (the briefing: on Demiurge it sets Today with `demiurge_today` and ends silent, elsewhere it is sent to Home), watch every fifteen minutes within the owner's existing hours (follow-through, gated on monitor changes), explore every two hours (one thing for the owner), continue every thirty minutes (handed-off threads, gated on monitor changes), evening (what has gone quiet). Recall governs live conversations; setup is loaded when the owner asks to change a routine, a responsibility or a grant.

Watch is follow-through: the conversation record notices, watch acts. It reads the injected "MONITOR CHANGE DETECTED" or "Monitor Baseline" block first, works due loops (relaying ready owed answers in the owner's words and handing promised work to continue), reconciles only the channel files shown as changed, then answers the dropped conversations the signal lists. Nudged waiting-loop ids stay in `$HERMES_HOME/records/watch/state.json`. Evening takes "answered elsewhere": for each open ask in `brain needs-you --json`, a channel or a task changing state may show it answered outside a conversation; evening resolves it with that evidence.

`brain watch-signal` is a deterministic, model-free monitor. Its stdout always has three headers in order, with sorted rows and no current timestamp:

```text
due:
<loop id> · <kind>[ · ready] · <text>
[last failure: <time>]
channels:
<account>/mail: <files in the two newest date folders> recent, newest <path>
<account>/calendar: <newest file> @<its mtime, epoch seconds>
unanswered:
<session id> · <source>
```

Due rows come from `loops.due`; a ready loop is marked, so marking one that was already due still wakes watch. While anything is due, both signals also print the routine's `last_failure` time from `$HERMES_HOME/cron/jobs.json`, so a run killed mid-chunk (a gateway restart, a provider error) retries at the next tick instead of waiting for the work to move. Mail rows use names only, because the sync rewrites old mail when its labels change: a new message is a new file in a date folder. Each calendar directory gets its newest file by modification time (relative to that directory, including date folders; ties sort by path), or an empty filename. Unanswered sessions come from a read-only, short-timeout query of `$HERMES_HOME/state.db`: non-cron/subagent/cli sessions whose last message is a user turn older than ten minutes and younger than 24 hours. Minute-floored cutoffs decide membership without entering stdout. A missing or unreadable optional database leaves that section empty; an engine error such as a missing vault fails the command.

`brain install-scripts` installs executable `watch-signal.sh` and `continue-signal.sh` under `$HERMES_HOME/scripts/`. They use the job's vault-repo cwd (or `VAULT_REPO` when set). Attach them with `hermes cron edit <id> --monitor-script <script>`. Hermes hashes exact stdout each tick and skips the model while unchanged; script failures count as errors, never changes. A successful watch check writes `$HERMES_HOME/records/watch/signal.json` with `checked` (ISO time), `due` and `unanswered` counts. Continue writes its `checked` and `due` heartbeat to `records/continue/signal.json`. Neither check time enters stdout. `brain validate` names a configured monitor job whose heartbeat is missing or over 24 hours old and gives the cron-list and script commands to diagnose it.

## Channels

`<agent_dir>/Channels.md` holds the registry table, columns `channel | whose | identity | reach | read | write | granted | status`: one row per account or channel the agent can reach. `whose` is `own` (the agent's), `owner` or `shared` (a friend's calendar shared with it); `reach` says how it is opened, an `op://` item name, a browser profile, a platform, never a value; `status` is `live`, `pending` or `revoked`. `brain channels [--json]` prints the rows; `brain channels sync` registers the completed grants in `connect list` output (stdin, or `--run` to call `connect list`) that the table does not know by reach, as `owner` rows reached by the `op://` item the grant wrote, for the agent to complete. The owner's session block lists the live rows as what the agent can reach; `brain state --json` exports them as `channels`; `brain validate` reports unknown vocabulary, a registry over 400 words, and any `op://` reference in the agent's notes that no row registers. `<agent_dir>/Channels/` is a log folder for the registry's dated history. A Google account the owner connected in Demiurge is a row whose reach is its folder under `$HERMES_HOME/channels/<account>/` (written by `demiurge sync-channels`) and the `demiurge mail` and `demiurge calendar` commands; watch reads only the files its monitor shows as changed, and explore reads files changed since its last run; both act only through the commands. Watch, midday, evening and Sleep 1 open the owner's channels the way each live row's reach says and never read or report a pending or revoked one; explore reads them as a source of things to do for the owner, never as something to report.

`brain channels mail --since <ISO datetime | YYYY-MM-DD> [--json] [--vault PATH]` lists new mail headers from those same live owner accounts' synced files. A date or a datetime without an offset uses `brain.timezone`; an offset is converted to that zone before selecting date folders. Only `mail/YYYY-MM-DD/` folders on or after that date are opened. Headers accept Demiurge's RFC2822 dates as well as ISO dates. Output is newest first, capped at forty, one line per message: date, account, from, subject, labels, path; bodies never enter output. Mail labelled CATEGORY_PROMOTIONS, CATEGORY_SOCIAL, CATEGORY_FORUMS, SPAM or TRASH is excluded, as is SENT or mail from any live owner account address. The rest is split: mail from people is listed one message per line (capped at forty); notices (CATEGORY_UPDATES, or a bot, no-reply, notification or mailer-daemon sender) are grouped one line per account and sender, showing the newest message and a count (capped at thirty senders), because a payment due or a security alert is in them but one service can send dozens. The final line counts people's messages, notices and senders, what was filtered (category, sent, before-since time, invalid header) and what the caps omitted; old folders are not read or counted. JSON is an object with `messages` (each with `date`, `account`, `from`, `subject`, `labels`, `path`), `notices` (the same fields plus `count`), `filtered` (counts `category`, `sent`, `before_since`, `invalid`) and `omitted`. Reading this command never advances prime's checkpoint. Both the Calendar block and the mail listing say what could be seen, so a briefing is never quietly blind: `coverage:` names the connected owner accounts and the last run of the `demiurge-sync` job (from `$HERMES_HOME/cron/jobs.json`), or why nothing can be seen (no owner account connected, the sync not set up or never run, the last sync failed, or older than two hours). The Calendar block says "Nothing on the calendar" when it is empty and "I can't see the calendar: <why>" when it cannot be read; outside a Hermes home both stay silent. Prime always writes one mail line in Primed and morning gives the calendar, mail and what is due a word each, even when empty.

## Handoffs

A task the owner handed off carries `- **Handed off:** YYYY-MM-DD · report in <where>` in its entry; `brain handoff T-nnn [--report <where>]` writes it (in the register's full entry, or the archive body when the register holds only a warm line) and sets a resting state to `in_progress`. `brain continue --due` lists the handed-off tasks that are open and not resting on the owner (`waiting_for_owner`, `set_aside`, `blocked`), oldest handoff first, with each task's Next line, and exits 1 when there are none; the continue routine checks every thirty minutes and starts with it when the monitor changes. `brain continue-signal` uses the same due-task helper and prints `date: YYYY-MM-DD` followed by sorted `<task id> · <state> · <full Next line>` rows. With nothing due it prints exactly `date: none`, so an idle profile never wakes. A changed Next line wakes the next chunk; the date gives a daily retry when a failed run wrote nothing. Handoff remains keyed on the owner's request, never the agent's own plan. `brain state --json` exports `handoff` on each task. The explore routine never picks a handed-off task.

## Needs you

**Remembering what was said.** The record the provider writes after each conversation (when it goes quiet, or at session end) carries two more fields. `workingTogether` holds the owner's corrections and directions about how to talk to them or work with them from now on, and is taken only from the owner's sessions. Each line is added, dated, to the `Working together` section of the owner's profile; a line whose words another already holds is skipped. The section goes into every session with the owner through the owner card (450 words). `noted` holds facts and plans someone stated, each added to that day's `Conversations/<date> Noted.md`. Anyone but the owner is quoted as a claim ("Kevin said: ..."), and Sleep 1 files the lines into their notes. Neither field costs a model call or adds to the wait for a reply: they ride on the record the provider already makes.

`brain needs-you [--json] [--vault PATH]` computes one owner list: bullets in CURRENT's `## Needs you` section, tasks whose effective state is `waiting_for_owner` (including archived open tasks), and access requests. Trigger rows are the agent's commitments, not owner requests, and are excluded. Asks sort before confirms; each kind keeps source order. Text output is `ask · text · source`; JSON includes stable IDs, kind, text, origin, since and source pointers. `brain needs-you --ask TEXT [--source NOTE]` adds an ask to that section; a repeat of an open ask is ignored; an ask is never refused. The list is ranked: asks before confirms; among asks, one naming a date in the coming week first, then what blocks work (a task waiting on the owner, a request relayed by another intellect), then the rest newest first. The owner sees the top five; `brain needs-you --overflow` lists the lowest-ranked asks past five, which the evening decides that night. `brain needs-you --stale` lists asks unanswered for 14 days or more, oldest first, for the evening routine to decide or retire. Each item carries `text` (the question the owner answers), `detail` (why it needs them and what a yes or a no means) and `context` (what it is about). A waiting task shows only its owner-facing lines: its text is its `**Ask:**` line (the proposition, cut at 16 words) and its detail its `**Why:**` line (cut at 40); with no Ask line the text is its title and the detail empty. Blocker, Status, Gap and Change are the agent's working notes and never shown. A task's context is its title, with its id keyed on the title so rewording the Ask keeps it. An ask's detail is an indented `  - why: ...` line under its bullet, written by `--ask ... --why ...`, cut at 40 words and removed with it. `brain validate` reports a waiting task with no Ask line, or an Ask or Why over its cap. `brain needs-you --resolve <id or text> --because <evidence>` removes one answered item from CURRENT's section (by id from `--json`, or by text matching exactly one open item) and appends `- date · kind · text · because evidence · [[source]]` to `<agent_dir>/Answered/YYYY-MM.md`, a log; tasks and access requests are refused, since they resolve where they live. The conversation record resolves answered asks immediately; evening checks channels, task state changes and outcomes that can be verified in the world. `brain needs-you --dismiss <id or text> [--reason no|done|stop-asking]` is the owner closing an item without answering it, from their app: the item leaves and is never listed again (dismissed ids in the Answered log are filtered out of `brain needs-you`, so a computed item such as an access request does not return). `no` (the default) sets an ask's or waiting task's task aside, declines an access request with no grant; `done` completes the task with the owner's word as evidence; `stop-asking` is `no` plus a signal the People review writes into Working together. The reason is the owner's choice, never inferred. `brain validate` reports more than five open asks. A CURRENT bullet that repeats a task already waiting on the owner (the same words, or a source naming the task) is shown once, as the task; `brain validate` names the bullet so it is removed, and names a Needs you bullet about the brain itself (a migration, the Hermes setup), which belongs in the Sleep Log.

**Ideas.** Proposals live in `<agent_dir>/Ideas.md`, an unpinned, warm orientation note with `## Open` bullets (`date · text · [[source]]`, optional indented `why:` and `needs:`), and in hubs' proposed improvements, which keep their Ask/Why lines and 16/40-word caps. `brain ideas` shows only the newest eligible idea; `--all` lists all open ideas, including snoozed ones; `--json` returns the shown item, counts and cooldown date. Every owner response starts a cooldown: one day for a new owner, seven for an established owner. New means the repo's first commit is less than 21 days old, by age alone, so an owner who wants little is not offered ideas at the new-owner pace forever. `brain ideas --add TEXT --source NOTE [--why TEXT] [--needs TEXT]` enforces the same one/seven-day spacing against the newest Ideas.md bullet and refuses duplicate open or rejected text. `--respond ID_OR_TEXT --answer yes|not-now|no|stop-asking` logs to Answered: yes creates a ready task handed off to Home; not-now snoozes for 14 days; no removes the idea and blocks re-adding it; stop-asking also records that preference for People review. Improvements become accepted or declined. Open counts include snoozed ideas. Validation checks Ideas.md's why lines and word caps; improvements still receive owner-question checks. Ideas have no added block in `.hermes.md`.

`brain stale-tasks [--vault PATH]` lists the open tasks the evening routine reviews, oldest first: untouched for 21 days, or 14 when waiting on the owner. A task is touched by a use, an inferred use or any date its entry names, so a deadline still ahead keeps it off the list. Set-aside tasks are already decided and never listed.

Outside CURRENT's generated active-threads markers, write:

```md
## Needs you
- 2026-10-28 · ask · Book the 16th return before Thursday? · [[Lisbon trip]]
- 2026-10-28 · confirm · Went ahead with the refundable fare.
```

The fields are ISO date, kind, text and an optional source wikilink, separated by ` · `. An `ask` is a decision only the owner can make; the agent may wait on it. A `confirm` records something already done so the owner can correct it; the agent never waits on one. Malformed bullets are ignored. `brain nightly --write` removes unanswered confirms dated seven or more days ago as accepted, and asks dated 28 or more days ago as retired, and records each removal in its report and Sleep Log. Preview changes only its disposable copy; rebuilding active threads preserves this section verbatim.

## Audit

`brain audit [--days 14] [--json] [--sessions-dir <dir>]` is the process view a maintainer can always see: notes by kind with word totals, each folder under the agent directory with its file and dated-file counts (a folder of dated files is the file-per-run smell), monthly ledgers with rows and mean words per row (a ledger of 120-word rows is writing disclaimers, not receipts), recent episodes with their mean size and how many exceed 1500 words, the directory's number of most active notes and their body-word total, and the compiled context word count, which day routines differ from the package defaults, each cron job's runs in the window with mean messages, tool calls, tokens, minutes and end reasons from the session store's own counters, and commits by type. Everything in it is a count, a size or a routine name; no note contents, titles or paths of knowledge notes. Ledger paths are process records and do appear. Finding routines that spend 60 tool calls to find nothing, or ledgers that grow by essays, starts here.

## Health

`brain health` prints an operational report built only from commits, engine state files and counts: the last run of each night stage with ok, stale or never (a stage is ok when its commit covers yesterday or later), installed against recorded engine version and any pending migration, yesterday's digest coverage line, validation problems, note counts by tier, open tasks, and the working tree against origin. `--json` gives the same as data; `--write` saves the committed copy to `<hermes_dir>/health.md` (without the working-tree line, so hourly refreshes only commit real change). The refresh script writes it every hour. An agent asked "how are you" by a maintainer answers from this report; nothing in it is a note's contents.

The validation count in `brain health` is everything `brain validate` names: structure and the hygiene checks (Needs you duplicates and machinery, Ask and Why lines, the Primed cap, the channel registry). The nightly gates its commit on structure only, and adds a `checks:` line to its report when hygiene problems remain; the evening routine runs `brain validate` and fixes the Needs you ones. One hygiene check keeps CURRENT current: an item whose newest date is more than two weeks old is named (not Needs you, sections titled History or Superseded, or the generated active threads), and Sleep 1 moves it to its note's History, moves a standing direction to its owning note, or rewrites what still holds with today's date. Another names a task that CURRENT or Primed still presents as live when the task's own record says it is completed or cancelled (outside History sections, comments and the generated active threads, and unless the line itself says it is done); Sleep 1 corrects or drops the line.

## Work snapshot

`brain state --json [--vault PATH]` prints a read-only snapshot of the brain's work: schema and engine versions, the vault's short Git HEAD (with `+dirty` for uncommitted changes, or null outside Git), tasks, hubs, routines, triggers, the last 30 days of ledger rows including today, needs-you items, the single shown `idea` (or null), `ideasOpen` (including snoozed ideas), and drafts/reflections. Without `--json`, it prints one line of counts. It writes nothing and has no dependency on its consumers, including Demiurge.

Schema 1 uses deterministic ordering and no generation timestamp, so unchanged vault state produces identical JSON on the same configured date. Fields are only added within a schema version; anything else bumps schema. Tasks retain one identity per ID, with register entries taking precedence over archived copies. Routine names use the latest ledger spelling, falling back to the responsibility hub's records value.

Hubs and outputs exclude the configured sources directory, the human profile's folder, people and agents directories, the Hermes directory, notes with `tier: private`, and notes with `kind: conversation`. These exclusions also apply to ledger discovery, needs-you source pointers, and ideas, so private proposals cannot leak through the owner queues. Resolvable needs-you links become vault-relative source paths, retaining anchors and IDs.

The additive `shareable` object exports audience-filtered hub titles, ledger receipts, and group member platform ids;
see [what each audience may see](access.md#what-each-audience-may-see-brain-state). It never includes person-specific
grants, note bodies, or outputs. The non-JSON count summary is unchanged.

## Parallel operation boundary

Run only one nightly process per vault. The engine assumes it is the only writer during `--write`.

## Commands

`brain shard-sessions <export.jsonl> <sessions dir>` splits a full Hermes JSONL export into `jsonl/<session id>.jsonl`, rewriting only shards whose bytes changed. The export script shards into `$HERMES_HOME/records/sessions/`, outside the vault; the digest and attribution read the shards there (and a legacy `all.jsonl` if one is still present). `brain paths records` prints the records root.

****Hermes toolsets.** Disabling Hermes's `memory` toolset also drops a memory provider's system-prompt block (`memory_manager.memory_provider_tools_enabled`); never disable it in a profile running the brain.

**Session kinds.**** Every exported session is classified as a conversation, a routine (a cron run: source or title begins `cron`), or an evaluation (title or source matches `Evaluation fixture`, `retrieval check` or `RC-nn`, or the first user message begins `Evaluation fixture:`). The digest includes only conversations unless `--include-routines` is passed; attribution ignores evaluation sessions entirely and takes only explicit citations, never observed opens, from routines. Paths under `<agent_dir>/Retrieval Checks/` never earn observed credit. The digest's `coverage:` line reports how many sessions of each kind were included or excluded and how many turns the word cap omitted.

`brain migrate-check` and `brain migrate-done` carry the agent's part of an upgrade: the package ships a Markdown prompt per version that needs one (see `src/brain/migrations/README.md`), `migrate-check` writes the applicable ones to `<hermes_dir>/pending-migration.md` after each nightly update and, when that file is new or changed, schedules one run of the agent two minutes out in the current Hermes profile (`hermes cron create 2m … --repeat 1`) so it starts at once, the recall skill makes the agent perform them, and `migrate-done` records the version. `<hermes_dir>/engine-version` is the recorded version, committed with the vault. `brain migrate-done --defer "<step>"` (repeatable) closes a migration while carrying a step the agent may not do unattended, such as an edit to a Hermes-protected file, for a maintainer in `<hermes_dir>/deferred-steps.md`: a maintainer's sessions are told how many wait, `brain health` counts them, and the owner's Needs you never carries machinery; a step that waits on a future event belongs in Triggers. `brain health` dates a pending migration from the commit that added the current file.

`brain update` upgrades the package from `update_source` using the interpreter that owns `brain`, then reinstalls the cron scripts and memory provider atomically per file. The export script runs it first every night, so a vault stays current without anyone touching the machine; a failed update is reported and the archive continues on the installed version. `brain paths python` prints that interpreter.

`brain session-ids <all.jsonl>` prints each session id once, and with `--with-kind` prints `id<TAB>kind` (conversation, routine or evaluation); the export script uses it to run one `hermes sessions export --session-id --force` per session, conversations into the vault and the rest into the records folder, because the directory form of the Markdown export needs a filter and otherwise exits 0 without writing, and without `--force` a session exported before is skipped with a success status. The script fails if any per-session export fails or fewer Markdown files exist than sessions.

brain validate

brain attribute [--sessions-dir <dir>] [--write]

brain compile-context [--out <path>] [--write]
brain retrieve "harbor CI" [--limit 12] [--json [--form names|snippet|full]]
brain session-context [--platform demiurge] [--user-id <handle>] [--user-id-alt <permanent id>] [--user-name <name>] [--chat-id <id>]

Every subcommand accepts optional `--vault <path>`. `python3 -m brain` is also supported. `brain paths` prints an absolute path: SOUL, rendered skills, installed scripts, provider or records directory, the active vault or repository root. `--sessions-dir`, `--file` and `--out` paths are relative to cwd, not the vault; adjust example session paths to your config.

`--date` is the Pacific date of the occurrence; `digest` requires it, while `nightly` allows omitting it for an ad hoc run. `attribute` prints explicit uses and JSONL observed on-demand reads, and `--write` appends them to monthly Use Logs. Rows are `timestamp | target | reason | explicit/inferred/observed/live [| confirmed/unconfirmed]`. `simulate` prints the spec's decay table.

`show-skill <routine>` prints the package's current text of one routine rendered for this vault, so an agent can adopt a changed day routine (morning, midday, evening, which the engine never re-renders) by hand, keeping its own steps.

`compile-context` prints generated context without writing unless `--write` is given. Its word count goes to stderr, with a non-fatal warning over 6000 words. Output defaults to the configured repository's `.hermes.md`; `--out` overrides this only when writing. Context includes frontmatter-free START, CURRENT and Triggers, only explicitly open task sections exactly as represented in the register, a directory starting with the most active notes and their index lines, followed by the existing names-only lists. The active block selects hot-tier notes, pinned first, then by descending activation and path, within `hot_words` (`BRAIN_HOT_WORDS`, default 6000) words of note body. Pinned notes may exceed the budget; an oversized unpinned note is skipped so smaller later candidates can still fit. Full archived warm-task bodies and overflow notes remain on demand through `brain retrieve`. Hot Set.md and Warm Index.md are retired; the nightly deletes any stale copies and reports their removal.

`retrieve` is read-only and deterministic, scoring title/path, index-line and heading tokens with tier weighting, then spreading one hop through local links. Task and trigger IDs receive direct matches. Logs, dreams, primed notes and Conversations are not retrieval candidates. JSON output is a list, empty when nothing matches; text mode prints `no candidates`. `--form snippet` adds each candidate's index line as `text`, `--form full` its body (a task match gives its own entry).

The session-export parser assumptions below are retained verbatim from the vendored engine documentation. Their literal default-layout examples (`memory/`, `agent/`, `../Conversations/Sessions`, and `vault.ORIENTATION`) now refer to the corresponding configured paths and orientation set. Name defaults now come from TOML before the environment overrides, and resolve per config load rather than module import. The installed commands run from the repository root, not `memory/.brain`.

### Session export assumptions

Attribution reads `$HERMES_HOME/records/sessions` unless `--sessions-dir` says otherwise. Attribution prefers `all.jsonl` (one object per session), even if empty, and otherwise recursively scans every `*.md` as UTF-8 (accepting a BOM and replacing undecodable bytes). It does not verify manifest hashes or interpret lineage; Markdown fallback adds no observed attribution. The exact export layouts remain unverified.

The Markdown parser is line-based, not a Markdown AST. Case-insensitive role markers include headings such as `## assistant` or `### Assistant`, bold names such as `**assistant**`, `assistant:`, and metadata such as `role: assistant` (also quoted or list-prefixed). The same forms recognize user/human, system, developer, tool and function roles; only the nearest preceding assistant marker permits a line whose first non-whitespace text is `Sources:`. If there are no recognized role markers anywhere in the file, all such Sources lines qualify. Sources text uses the existing explicit-use parser, including its orientation-note exclusion; surrounding prose is not inferred as reliance, and fenced examples are not specially interpreted.

Each row takes the nearest preceding valid ISO-8601 date-time in the file (minutes required, optional seconds/fraction/zone), otherwise the first valid YYYY-MM-DD in the filename, then the nearest dated parent directory, then the file's local mtime date. A date-time inside the Sources line itself is not preceding that line. The reason is `cited in session <file stem>`; rows are deduplicated within the export batch and against the relevant monthly Use Log by `(date, target, reason)`, regardless of timestamp time or source type. Re-exporting the same session stem is safe; renaming stems changes attribution identity. Review a report-only attribution against a real export before relying on a new export layout.

JSONL attribution reuses the digest's message/container, content and timestamp aliases below; timestamps are Pacific ISO date-times, inherited from the nearest preceding timestamped message, then session metadata, then the export filename/parent/mtime date. Assistant `Sources:` lines retain explicit parsing and `(date, target, reason)` deduplication, with reason `cited in session <id>`; IDs prefer `id`, then `session_id`, then the export filename and line number. Observed rows use `opened on demand in session <id>` and deduplicate by `(date, target, source=observed)` across all sessions and existing monthly logs, independent of session ID.

Observed attribution excludes `vault.ORIENTATION`, every note selected for the directory's active block when the directory section is enabled, and all paths under Conversations, agent/Dreams, agent/Explorations, agent/Use Log, agent/Sleep Log and agent/Tasks Archive. Loading is not use: automatic context and bookkeeping reads must not reinforce themselves just by being loaded.

Tool-call field names are assumptions, not a verified Hermes schema: assistant records are searched recursively through dict/list wrappers (including `tool_calls`, `function_call` and content tool blocks) for `arguments`, `args`, `input` or `parameters`, with names from `tool_name`, `name` or `tool`. Dict/list arguments and JSON-encoded strings are traversed recursively; any `memory/...md` path substring in an argument string counts as an opened note regardless of tool name (`read_file`, `search_files`, `execute_code`, `session_search`, MCP tools, etc.). Paths without spaces match `memory/[^"'\s]+\.md`; space-bearing names such as `memory/Harbor Context.md` are also accepted, ending at the first `.md` before a quote, newline or another `memory/` prefix. Only existing vault notes receive observed rows, and compacted calls and tool/function result messages never count; no success or semantic-reliance claim is inferred from a call.

For a named `terminal` call containing `brain retrieve`, shell quoting is parsed with `shlex` and the positional query is recorded instead of any reads from that call; `--vault`, `--limit`, their `=value` forms and `--json` are skipped. This is not a shell interpreter: malformed quoting yields an empty query, and dynamic shell expansion or unrecognized export argument fields are not reconstructed.

### Digest

`digest` is a separate command, not another step inside `nightly`. The default sessions directory is `$HERMES_HOME/records/sessions`, this profile's own export; until that folder exists, an existing `<vault>/Conversations/Sessions` is read instead so an older export script keeps working. It prefers `all.jsonl` from `hermes sessions export <file> --format jsonl`, even if empty; only when absent does it recursively read Markdown exports. Without `--write`, only the complete digest is printed to stdout. With `--write`, only the digest file is saved, and its path and retained conversation word count are printed. It never attributes uses, changes notes, or publishes anything.

Export field names remain unverified against a real Hermes export. The defensive JSONL assumptions are:

- Each nonblank line is one session object. Message arrays may be named `messages`, `history`, `turns` or `conversation`, at the root or under `session`, `metadata`, `data` or a `conversation` object; a wrapper's `metadata` is also checked. Nonobjects and malformed message entries are ignored; malformed JSON fails with the file and line number rather than silently losing turns. Files accept UTF-8 BOMs and replace undecodable bytes. No manifest or lineage deduplication is attempted; tool-call observations use the defensive parsing above.
- Message roles are case-insensitive `user` and `assistant` only. System, developer, tool and function messages are excluded. `compacted: true` (also `1` or their string equivalents) excludes a turn; `active: false` alone does not. String `content` is preserved verbatim, with `text` accepted when `content` is absent. Lists concatenate string blocks and `text`, `input_text` or `output_text` blocks without adding separators; missing block types with `text` are accepted, including a nested `text.value`. Tool and image blocks are ignored. Empty or unsupported content is omitted. Sources footers remain ordinary text, with whitespace untouched.
- Timestamps check `timestamp`, `created_at`, `created`, `ts`, `time`, `sent_at`, then `started_at`, `start_time`, `start`, `ended_at`, `end_time`, `end`, first on the message and then in `timings`. ISO-8601 strings and epoch seconds/milliseconds (including numeric strings; magnitude at least 100 billion means milliseconds) are accepted. Offset-free timestamps are assumed Pacific; aware timestamps use `zoneinfo`'s `America/Los_Angeles`, including DST. Invalid values are skipped. An undated message inherits the preceding usable timestamp, even from an excluded message. Leading undated messages are omitted if any message has a timestamp.
- Only sessions with no usable message timestamps can use a session-level range. Start aliases are `started_at`, `start_time`, `start`, `created_at`, `created`, `timestamp`, `ts`, `time`; end aliases are `ended_at`, `end_time`, `end`, `updated_at`, also checking session `timings`. Inclusion uses inclusive Pacific dates. A lone endpoint covers only its own date; missing or reversed ranges are omitted. Included turns receive the start time on its date, otherwise midnight, and a note explicitly marks these times approximate.
- Titles prefer `title`, `name`, `session_title`, then `id` or `session_id`; sources prefer string `source`, `platform` or `channel`. These are checked in the same wrappers, with headings normalized to one line. Missing metadata falls back to the export filename and JSONL line number (or Markdown relative path).

Markdown fallback reuses attribution's role and ISO timestamp recognition (including `human` as user), taking a preamble's first `#` heading as the title or otherwise the filename stem. Role-marker suffixes may carry inline content or timestamps; standalone or labeled timestamps before a turn's text are metadata. Fenced blocks and timestamps inside ordinary message bodies are preserved, not treated as metadata. Files with no recognized roles contribute nothing. When all message timestamps are missing, the filename/dated-parent/local-mtime date fallback is used with an approximate-time note. The parser is line-based; role-like lines outside code fences remain ambiguous, so review a real export before depending on its layout.

Turn labels use `BRAIN_HUMAN_NAME` (default `Human`) and `BRAIN_AGENT_NAME` (default `Agent`), resolved once when the script starts. These environment variables affect display labels only, not paths or export role parsing.

After each assistant turn's original text, `reads: <paths>` lists distinct tool-call note paths in encounter order since the preceding text-bearing assistant turn in that session; textless tool-call messages accumulate into the next such turn. Each retrieval adds `retrieve: "<query>"` on its own line, with JSON string escaping; tool results never add reads, and digest reads include automatic notes even though observed attribution excludes them.

Sessions are ordered by their first retained timestamp; turns within each session are chronological, with stable input-order ties. `--max-words` (default 25000, nonnegative) counts whitespace-separated words of retained message text only, excluding frontmatter, headings, turn labels, fallback notes, reads/retrieve annotations and the truncation notice. It selects a chronological prefix across all sessions, stopping before the first whole turn that would exceed the cap, then groups those turns into session sections. The header counts only represented sessions and retained conversation words; a final truncation line counts every remaining turn. The generated date is today's Pacific date: identical inputs on the same generation date produce identical bytes, and unchanged files are not rewritten; regeneration on a later day updates that header date.

## What `nightly` does, in order

**Digest (before the pass).** The nightly export script runs `brain digest --date YYYY-MM-DD --write` after exporting sessions. It then runs `brain redact` over the session transcripts and digests before committing: well-known key shapes (Google, OpenAI, Anthropic, Stripe, Slack, GitHub, AWS, private-key blocks) and values assigned to secret-named variables become `[REDACTED:<kind>]`, so a credential pasted into a conversation is never pushed. Sleep 1 reads `Conversations/Digests/YYYY-MM-DD.md` for consolidation before invoking `nightly`.

1. **Rollover.** Create this month's Use Log, Sleep Log and Tasks Archive files if missing.
2. **Frontmatter defaults.** Every mechanical note gets `kind`, `tier`, `pinned`, `uses`, `uses_inferred`; a new hub, profile, reflection, episode or primed note gets today as its first use. Logs, dreams and daily archives are left alone. Retired generated views are removed before the pass.
3. **Load tasks.** One `Task` per ID. A generated `- **Warm:**` line in the register is replaced by its archive body; a full register entry is canonical over the archive; a duplicate ID keeps its first entry. Archived open tasks the register does not list are loaded too.
4. **Attribute sessions, then fold uses.** When `--sessions-dir` is given, append new assistant Sources citations and JSONL observed reads to the relevant monthly Use Logs first. Every dated row in `agent/Use Log/*.md` is then credited to its target: explicit rows into `uses`, inferred and observed rows into `uses_inferred` (half weight), task citations into the register comment. An explicit note use supersedes an observed use on the same date, including previously folded observed credit; observed rows never credit tasks, which rely on citations or triggers. Rows are skipped when future-dated, `MISS`, a trigger, `live | unconfirmed`, or aimed at a log, dream or daily archive. Credits are date sets, so folding the same row twice changes nothing.
5. **Activation and tiers.** ACT-R base-level activation from the use dates; hot, warm or cold per the spec. Pinned stays hot, unconsolidated conversation records cannot go cold, an expired Primed note goes cold.
6. **Triggers.** Fire date commitments (a fired commitment adds a use to its task), mention once and then retire intentions whose source went cold.
7. **Write.** Save changed notes. Place each open task: hot as a full entry bounded to 150 words with older evidence archived, warm as one line with the full body in `agent/Tasks Archive/T-nnn.md`, cold as archive only. All open tasks remain named in the directory, including archived ones. Rebuild CURRENT's active-threads block. Remove any retired Hot Set.md and Warm Index.md generated views.
8. **Compile context.** Rebuild the repository-root `.hermes.md` from the source notes, with the most active notes at the start of its directory, and report its word count (warning, not failure, above 6000 words).
9. **Validate.** Required frontmatter, resolvable wikilinks on changed notes, pinned notes hot, superseded headers present. On failure: print, append a failed entry to the Sleep Log, exit 1, no commit.
10. **Record and publish.** Append the report to the Sleep Log. With `--commit`, stage the configured vault minus legacy `.brain` state plus repository-root `.hermes.md` and commit as `sleep1(<date>): <summary>`. With `--push`, `git pull --rebase origin main` then push; a conflict aborts the rebase and exits non-zero with nothing pushed.

Without `--write` the same pass runs on a temporary copy of the agent tree and only prints the report.

## Idempotence and interruption

Every step is a function of the files as they are. Running the same date twice produces the same files, apart from a second Sleep Log entry. A run killed halfway leaves some notes saved and others not; the next run converges, because nothing depends on a cursor, a marker or a prior receipt. If a run must be undone, `git revert` the commit.

## What it does not do

Read Gmail or any connector, capture conversations, judge salience or surprise, infer reliance, write facts, or decide anything about the owner. Those are the agent's judgment steps in the routine files. The script is the same every night; the judgment is logged and audited by Sleep 2.

## State

- Note frontmatter: `tier`, `activation`, `uses`, `uses_inferred`, `pinned`, `consolidated`, optional `index_line`.
- Register comments: `<!-- brain: state=ready; uses=...; inferred=...; tier=...; activation=... -->` under each `### T-nnn` heading. `state` is `ready`, `in_progress`, `blocked`, `waiting_for_owner`, `set_aside`, `completed` or `cancelled`; a task is open unless completed or cancelled. `set_aside` is open and recoverable but never in `needs-you`, Sleep 2's nudges or `stale-tasks`. `yours` is the owner's own work: open, never in `needs-you`, never continued as a handoff, listed by `stale-tasks` after 14 quiet days so the evening can ask once whether it is still on, done or dropped. `brain task T-nnn done|drop|yours [--why ...]` changes one task for the owner (completed, cancelled, or yours), with a dated line. Written states are normalised (case, spaces and hyphens; `done` is `completed`; `parked`, `deferred` and `deprioritized` are `set_aside`). Legacy comments without `state` keep their meaning: only `status=open`, or no status, is open. `state` wins over `status`, which is dropped on rendering; the engine never invents a missing state. `brain validate` reports an unknown state; the nightly never gates on one, so a mistyped state cannot stop the night's commit.
- Task fields: `- **Status:**` keeps the human-readable detail; optional `- **Hub:** [[Target]]` names the hub the task serves. Labels and anchors are allowed (`[[Target|label]]`, `[[Target#anchor]]`); the hub is `Target`.
- Legacy `.brain/state.json` (not managed or required by the package): only `channels`, the Gmail acknowledged-coverage checkpoints described in [[memory/agent/Channels|Channels]]. The agent maintains it; the script never reads or writes it.
