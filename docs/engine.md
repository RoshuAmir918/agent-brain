# Agent Brain engine

The [runtime contract](runtime.md) defines what the engine and its runtime exchange. `brain schedule` declares routines in `schedule.toml`: list or check them, import existing runtime jobs, and set, remove, pause or resume a routine. `brain paths schedule` prints the configured file path. Release 0.29.0 only declares the schedule; the runtime adopts it in its own release.

Agent Brain is an installable Python package for the arithmetic half of remembering. Vaults contain notes, not a vendored engine. The judgment half lives in the vault's Memory Spec and routine skills.

Git is the ledger. Each nightly stage is one commit, so `git log --grep` says whether a stage ran, the first missing commit is where a resume continues, and `git revert` undoes a stage. A local commit can remain unpushed; a clean working tree only proves there are no local changes.

## Installation and updates

Python 3.11 or newer is required. From a source checkout:

```sh
python3 -m pip install .
# For development, including tests:
python3 -m pip install -e '.[test]'
brain --help
```

Install a built wheel on another machine with `python3 -m pip install /path/to/agent_brain-0.1.0-py3-none-any.whl`. When releases are available on your package index, use `python3 -m pip install -U agent-brain`; no index publication is implied by this checkout. An updated source checkout can instead be installed with `python3 -m pip install -U /path/to/agent-brain`.

Run these from the vault repository after installation or an upgrade:

```sh
brain install-skills
brain responsibility "<Name>" --skill <name> [--records <folder>]
brain install-scripts
```

`install-skills` renders the routines into `<vault>/<runtime_dir>/skills/<skill_prefix><routine>/SKILL.md` and prints the absolute directory the runtime reads. The core routines (attribute, sleep1, sleep2, rem, recall, improve, people, explore, watch) are overwritten on every run so package updates reach them, except for a `## Local` section at the end of the rendered file, which is carried over verbatim: the vault's own additions live there. The day routines (morning, midday, evening) are written only when absent, so local edits survive. `brain install-skills --force` resets the day routines to the package versions. Templates are shipped in the wheel; edits to rendered copies are overwritten. Rendering uses literal token replacement, not Python format strings. `install-scripts` copies the packaged shell scripts to `$AGENT_HOME/scripts`, makes them executable and prints the installed paths. None of these commands edits global config or schedules jobs.

The runtime supplies `VAULT_REPO`, `AGENT_HOME` and a PATH containing `brain` and `demiurge`; see [the runtime contract](runtime.md). `refresh.sh` pulls the notes, compiles `.context.md`, renders skills and copies the configured SOUL into `$AGENT_HOME`. `export-sessions.sh` archives conversation transcripts into the vault, routine transcripts and every JSON shard into `$AGENT_HOME/records/sessions/`, builds yesterday's digest, redacts published transcripts and invokes refresh. These retain the existing commit/push behavior: executing them is a publishing operation, unlike the install commands. No script is run by installation.

## Configuration

Place `brain.toml` at the vault repository root. All keys are optional and merge with these defaults:

```toml
[brain]
vault = "memory"
agent_dir = "agent"
people_dir = "people"
agents_dir = "agents"
human_profile = "human/Profile.md"
sources_dir = "sources"
runtime_dir = "Runtime"
human_name = "Human"
agent_name = "Agent"
owner_user_ids = []
maintainers = []
log_dirs = []
skill_prefix = "brain-"
update_source = "git+https://github.com/RoshuAmir918/agent-brain"   # "" disables auto-update
```

`vault` and `sources_dir` are relative to the repository root. The agent, people, agents, human profile and runtime paths are relative to the vault. `sources_dir` remains read-only. `Archive/` is a supported read-only sibling link namespace; it is not a new config key. Layout paths must be relative without `..`. Tasks, Triggers, CURRENT and the other note basenames remain fixed. Generated wikilinks use the configured `vault` prefix. `BRAIN_HUMAN_NAME` and `BRAIN_AGENT_NAME`, when set, override the configured display names, including rendered skills.

`timezone` is the owner's IANA zone, default `America/Los_Angeles`: the export script's "yesterday" (`brain timezone` prints it; `BRAIN_TZ` in the environment overrides), digest day boundaries and timestamps, and the default date of `health`, `audit` and `nightly`. A profile whose owner sleeps in another zone than the host must set it, or the 00:30 export lands on the wrong day.

`BRAIN_TODAY=YYYY-MM-DD` in the environment pins the engine's today, for evaluations against throwaway vaults: every command that computes today or an age from it (`state`, `needs-you`, `loops`, `stale-tasks`, `nightly`, `digest`, `health`, `audit`, `session-context` and runtime calls, the scripts' dates) uses it, and a ledger row or conversation capture without `--at` takes that date with the current time of day in the configured zone. An explicit `--date` or `--at` still wins. A value that is not a date fails every command.

An optional `[context]` table sets what enters an agent's context. Each key has an environment override, and the environment wins over `brain.toml`:

```toml
[context]
hot_words = 6000          # BRAIN_HOT_WORDS: the directory's active-note body-word budget and compile-context's warning
sections = ["before", "start", "current", "primed", "goals", "triggers", "upcoming", "tasks", "library", "directory"]   # BRAIN_CONTEXT_SECTIONS, comma-separated
prefetch = true           # BRAIN_PREFETCH (0 or 1)
prefetch_limit = 6        # BRAIN_PREFETCH_LIMIT: notes recalled per message
prefetch_chars = 1500     # BRAIN_PREFETCH_CHARS: the recalled block's cap
prefetch_form = "names"   # BRAIN_PREFETCH_FORM: names, snippet or full
hot_threshold = 7         # BRAIN_HOT_THRESHOLD: days a single use stays hot
warm_threshold = 28       # BRAIN_WARM_THRESHOLD: days a single use stays warm
people = "card"           # BRAIN_PEOPLE: off, line or card; what prefetch adds for a person named in the owner's message
```

`sections` chooses which parts of `.context.md` load, never how each renders: `before` is the engine's Before-answering paragraph (look again at what is loaded before a plan, advice or a person; a parked task has no question; a reminder is a Triggers row), `start`, `current`, `portrait`, `primed`, `goals`, `triggers` and `tasks` are those notes' blocks (Portrait and Primed are skipped until the vault has them; Goals shows capture guidance when absent), `upcoming` is the engine's scan of dates in the next seven days, `directory` starts with the most active notes and their index lines, followed by the names-only directory. The legacy section name `hot` is accepted as an alias for `directory`; the header and closing line always remain. `prefetch_form` `names` is the default block of paths and reasons, `snippet` replaces each reason with the note's index line, and `full` gives each note's body; both are cut to `prefetch_chars`. The thresholds also set `brain simulate`'s defaults. Unknown keys or sections, non-integers and unknown forms fail every command. The runtime uses these settings through the commands in [the contract](runtime.md).

`library`, after `tasks`, renders the runtime's `$AGENT_HOME/works/LIBRARY.md` under `## Library`, without its own `# Library` title. It keeps the first forty work lines, every refusal, conflict and error notice, and a pointer to the full listing when capped. It is silently omitted when `AGENT_HOME` is unset, the file is absent, or it holds no works or notices. An explicit `[context].sections` list replaces the default: add `library` there to enable it. `BRAIN_CONTEXT_SECTIONS` overrides that list, and `compile-context --sections` only narrows the allowed sections.

In 0.50.0, listing rows may append `| created YYYY-MM-DD | opened YYYY-MM-DD` (or `opened never`) after updatedAt. `works.parse` reads the title, slug, form, status, editability and those dates; absent or invalid dates are unknown. The night reads the full listing, independently of context's forty-work cap. Under the vault lock, alongside the Needs you cleanup, it asks once about each editable draft marked `opened never` that was created at least seven days ago: `Still want <title> in your Library? I can keep it, keep it updated, or put it away.` Opened, kept, read-only, younger and legacy rows are skipped. The source is `CURRENT#Library/<slug>`: it resolves to CURRENT and carries no task, so the ask lapses after five days. `$AGENT_HOME/records/library/asked.json` maps each asked slug to its first ask date (`{"nyc-deal-campaign": "2026-11-12"}`); each update uses an atomic rename under the same lock, and the record survives resolution, dismissal and lapse. An unreadable record skips new Library asks and is reported. An interrupted write can recover the date from an existing ask's source. Preview copies this record to its disposable tree and never marks the real record. An owner's answer keeps the work, keeps it with a proposal to make it a responsibility's living work, or retires it, then resolves the ask; recall directs the agent to `demiurge works --help` for the runtime's available commands. Opening keeps a work; retiring still-unopened drafts at fourteen days (restorable) belongs to the backend.

In 0.52.0, a work can keep an optional summary at the top of its Library page. `brain works view <slug>` reads JSON on stdin, `{"pieces": [...]}`, checks and cleans it with the same validator and kit as task views, and atomically writes `$AGENT_HOME/works/<slug>/view.json`. The slug must match `[a-z0-9-]+` and its folder must already exist (created by `demiurge works new`); the engine does not create works. The kit has `numbers` (with optional trends), `progress`, `table`, `checklist`, `places`, `links`, `gallery`, `steps` and `schedule`, with at most six pieces, 200 characters per string and 16,000 bytes in all. Errors print the kit and leave an existing summary untouched. Success prints `<slug> view saved: N pieces`; `{}` or `{"pieces": []}` removes the file and prints `<slug> view removed`. The file is versioned with the work and the app reads it like any other file; the harness saves it to the owner's Library after each run. A living work or a large table or collection keeps a summary of what matters at a glance, updated in the same chunk that changes what it summarises; a one-off document needs none.

`owner_user_ids` is a list of strings, default `[]`, containing the owner's platform user IDs. An entry `platform:id` (for example `demiurge:k57...`, the permanent Demiurge id) matches only sessions on that platform; a bare entry matches any platform. Either the primary or alternative session ID can identify the owner; display names and chat IDs cannot. This key does not change skill template values.

`maintainers` is a list of platform user ids in the same form as `owner_user_ids`, default `[]`, for the humans or agents who keep this brain's machinery running without being its owner: whoever set it up, or an agent that runs a nightly briefing. A session from one of them gets the maintainer block, followed by the current `brain health` report. The block tells the agent to talk to a maintainer about its work as to a colleague on the same machine, in plain words ("we were setting up access to the X site for the owner and it keeps failing because of Y"), to hand over process records on request (`brain health`, `brain audit`, ledger lines, its skills, the declared schedule), and to do engine maintenance on request without the owner: `brain update`, `migrate-check`, pending migrations (a step that asks the owner a question is carried to the owner by messaging them, since the owner is never an outside party; a step that creates a routine is the engine's instruction, not a schedule change), skill and script reinstalls, `validate`, `health`, `audit`, a restart of its own gateway, and committing and publishing the engine-state changes these produce. What it does not pass along is the owner's content: what they said, what their notes say, the people in the vault and their lives, credentials, transcripts, digests. The reason given is flow, not access: whatever the agent posts becomes part of the maintainer's memory and may reach whoever they talk to next. A maintainer holds the schedule of the engine's routines (night stages, export, refresh, improve, people, watch, explore, template day defaults) and the agent applies their create, move, pause, resume, remove or combine request in that session; the briefing hour and any routine the owner asked for by name stay with the owner. A maintainer cannot grant permissions or credentials, or edit notes. Add the key with the engine version that introduced it or later installed: older engines reject unknown `brain.toml` keys.

`log_dirs` is a list of folders under `agent_dir`, default `[]`, whose files are records rather than notes: receipts, ledgers, results. They join the engine's own ledgers (Explorations, Use Log, Sleep Log, Tasks Archive, Research) as kind `log`: never activated, never among the directory's most active notes, never link-checked. A note anywhere else can declare the same by putting `kind: log` in its frontmatter. Add a folder here as soon as the agent starts filing process artefacts in it, or they compete with knowledge for the hot budget.

The rule behind it: a routine owns three places, a state file it overwrites, a monthly ledger it appends one line to, and the notes it feeds knowledge into, never a file per run. Priming follows it: Sleep 2 overwrites `<agent_dir>/Primed.md` nightly; the older dated `Primed/` folder is still recognised and expired.

Routine ledgers live at `<agent_dir>/<Routine>/YYYY-MM.md`, with `kind: log`, `tier: cold` and five columns: `when | routine | outcome | account | next step`. `when` is a date or local date and time (`YYYY-MM-DD HH:MM`); outcome is `done`, `progress`, `waiting`, `blocked`, `failed` or `nothing`. Keep each entry under 25 words. Older four-column `when | routine | account | next step` rows still read, with no structured outcome.

`brain ledger append <routine> --outcome nothing --account "Nothing new." [--next "..."] [--at "YYYY-MM-DD HH:MM"] [--vault <path>]` appends in the configured timezone and prints the path. `--json` instead reads one object from stdin with `routine`, `outcome`, `account`, and optional `next` and `at`. The writer sanitises whitespace and pipes, finds a routine's folder from its existing rows (so `morning` can live in `Letters`), or creates `<Routine>` with its first letter upper-cased. Add a new folder to `log_dirs` yourself; the command never edits `brain.toml`.

`--skill <name>` instead of a routine names the cron job's skill; the engine maps it to the routine (a responsibility hub's `records`, else the skill without `skill_prefix`). The night stages (attribute, sleep1, rem, sleep2) are skipped: each is one commit, and git is their ledger.

**After the session.** The runtime reads `brain record-spec --json` and makes the structured record call described in [the runtime contract](runtime.md). A cron run, when it ends, becomes one row in its routine's ledger through `brain ledger append --skill`; its schema and ledgers are unchanged. A conversation, once quiet for 90 seconds or ended, sends only its new turns through `brain journal append` to capture loops, closures, answered asks and ready relays, a needs-you question, access requests, Working together directions and Noted facts. `next` and `thought` remain in the schema for compatibility; the model is no longer asked for a thought. An outcome of `nothing` with no capture or open work writes nothing. Diary rows stopped in 0.25.0; old `<agent_dir>/Journal/YYYY-MM.md` files remain as history. Their format is `when | platform | outcome | headline | next step`, with optional indented `needs you`, `touched` and `thought` lines. `brain journal recent [--count 30]` still reads them, and `brain journal append --synthesis` still writes a catch-up from stdin. A `needsYou` becomes an ask in CURRENT; touched titles that do not resolve or would be withheld by the export are dropped. The record sees existing asks with their ids and up to 20 open loops. Its conversation-only `resolved` and `ready` arrays each hold at most five ids or exact texts: `resolved` removes asks answered or made moot here through `needs.resolve`, with the reason "answered in conversation"; `ready` marks owed loops whose answer the owner just gave, for watch to relay. Already gone asks or closed loops are harmless on a retry. Work already carried by an open task, including a handoff's report, stays with that task rather than becoming another loop. Routines exclude these fields, as they do `loops` and `closed`.

**Loops.** `<agent_dir>/Loops.md` is a warm, unpinned orientation note, headed `# Loops`, with `## Open` and `## Closed`. The after-conversation writer adds `- YYYY-MM-DD HH:MM · promised|owed|waiting · <text> · [[source]]`, optionally followed by indented `with:`, `due:` and `ready: YYYY-MM-DD HH:MM` lines. Sources use the first public touched note, otherwise `Conversations`. Closed bullets carry `closed: YYYY-MM-DD HH:MM · done|dropped · <because>`; the latest 50 stay in Closed and older ones move to `Loops/YYYY-MM.md` logs by closing month. IDs are stable from kind and normalized text; repeated open text is ignored.

A loop's counterpart is the person or intellect by name who asked or was asked, never a role, team or system. Owed and waiting loops require `with`; promised loops may omit it. Owner names (the configured full name, first name and owner profile names) are refused: put the decision or answer in Needs you as an ask. Known counterparts match people or intellect profile folders, titles or aliases, or a unique profile first name, case-insensitively with underscores and hyphens treated as spaces; intellect names in Demiurge's cached directory also count. Vaults without a people directory accept other counterparts. Refused additions print one reason to stderr and the remaining conversation record still applies. Capture one loop per matter, retain every named deadline (including expiry and proceeds-unless-declined dates), and omit work already carried by tasks and things finished or answered in the conversation. Conversation closures are objects with `loop` (id or exact text), `outcome` (`done` only for work shown to have happened, `dropped` for cancellation, changed minds or moot work) and `why` (a plain reason under 120 characters). The writer stores that outcome and reason; legacy string closures still mean `done` with reason "closed in conversation".

`brain loops` lists open work; `--json` returns `open`, `due` and `closed_recent`. `--due` always exits 0; `--quiet` prints nothing and exits 1 when nothing is due, 0 otherwise. Add with `--add TEXT --kind K --source NOTE [--with WHO] [--due "YYYY-MM-DD HH:MM"]`; close with `--close ID_OR_TEXT --outcome done|dropped --because TEXT`. Explicit due dates become due at local midnight, or at their named time; without one, promises and owed answers become due after four hours. Waiting loops get at least 24 hours before attention, and a future due date still holds them back. `loops.ready(config, which, at)` makes any open loop due immediately, whatever its kind, age or deadline; it preserves the first ready time on retries. Watch works from `brain loops --due`; validate names open loops older than 14 days. The owner's state export includes `loops` (id, kind, text, with, due, ready, since, source) and `loopsClosed` (ten recent closures, with closed date, outcome and because), using the same source privacy boundary as Needs you. `journal` remains in the export for one more release.

Every engine write to a shared file holds a per-vault lock under `~/.cache/brain`, outside the vault and independent of `TMPDIR`. Records can land after the agent's commit, so pulls use `--autostash`. The runtime owns model calls and recording cadence; see [the runtime contract](runtime.md).

`brain nightly --write` collapses two or more `nothing` rows per routine per past day into one: `2026-10-27 08:30–22:30 | watch | nothing | 14 runs, nothing new. | ...`. Counts and time ranges survive a later collapse. Other outcomes, legacy rows and today or future rows stay untouched; preview changes only its disposable copy. Engine logs with different schemas (Use Log, Sleep Log, Tasks Archive, Research, Explorations, Improvements, Retrieval Checks and Loops) are not routine ledgers.

Discovery walks upward from an explicit `--vault`, or from cwd when omitted, choosing the nearest `brain.toml`. Without `--vault`, the vault is `<config repo>/<vault>`. With it, the given path is the vault root, while the discovered config supplies its layout. Without any config, defaults apply; the repository root falls back to Git's top level, or the explicit vault's parent / cwd when outside Git. No identity or setup interview is required by the engine.

## Editions

`edition` in `[brain]` is `personal` (the default: one person's intellect) or `enterprise` (an organisation's, getting its work done). It is the same engine; an edition decides what is installed:

- **Skills.** A skill's frontmatter may say which editions it is for (`metadata.runtime.editions: [personal]`); unsaid means every edition. `morning`, `people` and `prime` are personal only, and `brain install-skills` removes an earlier render of one when the vault is enterprise. Inside a shared skill, a part for one edition sits between `<!-- personal -->` and `<!-- /personal -->` (or `enterprise`) lines of their own; the render keeps this edition's parts without the markers and drops the rest. A personal vault's skills render exactly as before editions.
- **Context.** An enterprise context leaves out `primed` by default and always omits personal goals. It keeps `portrait`, the organisation's.
- **Routines.** `brain schedule init` adds the routines this edition starts with (the night's memory passes, the session export and context refresh, watch, explore, improve and evening; personal adds people, prime and the morning briefing) and never changes a routine already scheduled.
- **Checks.** `brain health` does not expect the people and prime stages, and validation keeps no owner profile, in an enterprise vault.

In enterprise, what is said to the intellect is visible to the whole organisation by stated policy, and it keeps no patient data, credentials or production records in notes (recall's "Talking to your colleagues").

**Per-task owners.** In an organisation's intellect a task is the person's who handed it off. The runtime names the person a turn is with in `BRAIN_SPEAKER` (`<platform>:<id>`, e.g. `slack:U0123ABC`); `brain handoff` records them on the handoff line (`- **Handed off:** 2026-11-06 · for slack:U0123ABC · report in …`), or `--for PERSON` names them. A handoff that names nobody keeps the task's owner, and `task set --report` never drops it. A personal intellect never writes one: all its tasks are its owner's. A task's Needs you items are for its owner (`owner` in `brain needs-you --json` and the state export; `brain needs-you --for PERSON` lists one person's), and `brain state --json` tasks carry `owner`. `brain continue --engaged T [--by PERSON]` counts only the owner's engagement: another person asking about the task leaves its budget as it is. **Members.** An organisation's intellect talks only to its members: the door (the Slack bridge, the stage's sign-in) admits only them, so in an enterprise vault anyone the runtime names is a member, except a maintainer, another intellect (its own block, as before) and a routine's own run. The session block says who they are ("This session is with Kim Lee, a member of Acme."), that what is said is visible to the whole team, and that work they hand off is theirs; `human_name` is the organisation. The operator (`owner_user_ids`, or the command line) is a member who may also change the setup. A member counts as the owner of their own conversation in the journal and is not logged as an outsider.

## Runtime context

The runtime calls `brain session-context` at conversation start as described in [the contract](runtime.md). CLI sessions and either ID in `owner_user_ids` receive only an owner identification. When `<runtime_dir>/pending-migration.md` exists, the owner's sessions, a maintainer's and the agent's own cron runs (platform `cron`, no user) also receive a notice to perform it in that session, drafting anything the owner must answer rather than stopping, and to finish with `brain migrate-done`; a session with anyone else never does. A cron run otherwise receives nothing. A third party is matched in `<people_dir>/*/Profile.md` bodies, not frontmatter. First by a line qualified with the session's platform (``- **Demiurge:** `<id>` ``, `Demiurge: <id>`; label case-insensitive) whose value starts with either session ID; only when no profile has one, by whole-token IDs anywhere in the body, where an email local part does not count as a handle. A prose mention in another profile therefore cannot make a qualified match ambiguous. One match supplies the profile (at most 250 words, with an ellipsis when truncated and a full-path pointer), applicable person/group/anyone disclosure rows, and the default denial rule. Missing Disclosure.md is explicit. Oversized rule sets are not partially injected: the block requires opening Disclosure.md before any disclosure. Unknown and ambiguous identities receive the stranger warning; ambiguous matches are listed. Without platform or IDs, no block is injected. The session block stays around 400 words.

Demiurge's identity directory is cached outside the vault at `$AGENT_HOME/records/directory.json`. `brain people sync` reads `demiurge intellects --json` from stdin, or runs it with `--run` (also done by hourly refresh); it reconciles id-less profiles only through explicit handles of the right kind, never display names or existing ids. `brain people who <id-or-handle> [--json]` identifies a person or intellect and names any profile carrying their id. For an unmatched Demiurge sender, session context adds the directory identity before the existing stranger warning, granting nothing; matched profiles keep their existing behavior. The hygiene check in `brain validate` lists Demiurge ids shared by multiple people or intellect profiles so they can be merged.

Before each owner message, the runtime calls `brain retrieve --json` and `brain people-mentioned`; [the contract](runtime.md) defines the calls. `[context]` sets retrieval limits, form and the people pointer.

`people` adds a pointer when the owner's message names someone with a profile under the people directory (whole word, full name or first name, case-insensitive), once per person per session and only in the owner's own sessions (a friend asking about a friend never has that person's profile put in front of the model): `line` is one sentence per person from the first line of their profile with the folder path, `card` the profile cut to 150 words plus the newest history entry, `off` nothing. It is the `brain people-mentioned --form <form> -- <text>` command, run by the runtime before recall.

An intellect registered under the agents directory is recognised from a platform-qualified id line on its profile (`- **Demiurge:** `<id>``), else any id line; its session block names it as an intellect, names its owner from the profile's `Owner:` line (a wikilink or a name), says its words are claims (and, for any known person, that a request which needs the owner is put to the owner now and the person told, never offered and left), resolves inline what its owner may learn (`brain access` for that owner; with no resolvable owner, nothing beyond what anyone may learn and an ask to the owner), and carries the relay rule: a request it relays for the owner is the owner's mail, put to the owner now (on Demiurge with `demiurge_tell_owner`, `text` when it should reach their phone; elsewhere an ask in Needs you), answered in the room with "asked", never acted on before they answer, never held for a briefing, and granting nothing. A stranger on Demiurge gets the same relay rule and the lookup rule first: `demiurge intellects` in the shell before treating the sender as a stranger, a profile from the template when it is one, and identity doubt is about a claim that contradicts the directory, not a sender the vault has not recorded.

Injected text is **never attribution credit**, including automatically injected profiles and disclosure rules. Only notes the agent subsequently opens on demand are eligible for observed attribution under the usual exclusions; loading pointers does not count as use. Disclosure text is guidance for the agent, not a retrieval access-control filter.

Set `owner_user_ids` in `[brain]` to the owner's permanent platform IDs. Verify identity with `brain session-context --platform demiurge --user-id <id>`. Runtime setup and file ownership are defined in [runtime.md](runtime.md).

## Today for the owner

`<agent_dir>/Memory Spec.md` is the engine's description of how memory works, so `brain install-skills` re-renders it from `templates/memory-spec.md` with the skills, keeping the vault's frontmatter and its `## Local` section.

Two sections of `.context.md` carry the owner's day into every session. **Primed** (`<agent_dir>/Primed.md`, kind `primed`) is judgment: the prime routine overwrites it each morning, after the People review and half an hour before the briefing (the morning routine then reads only the mail that arrived since prime's checkpoint), with where the owner is and with whom, what they said they would do, the people with something happening this week, what is held and waiting for them, the notes likely to come up and at most one nudge. `compile-context` loads at most its first 300 words, cut at a line, and `brain validate` reports a longer one. It follows CURRENT, is never a retrieval candidate and never enters the directory's active block. Prime also runs `brain channels mail --since <last_run>`: its checkpoint is `last_run`, an ISO datetime in `$AGENT_HOME/records/prime/state.json`, defaulting to yesterday at 06:30 in the owner's zone. It opens only headers suggesting a person needs the owner today, a deadline, a booking or a change of plans; important facts go into the owning task as in watch, never copied message bodies. At most three one-line facts bearing on today enter Primed's Today part. After writing Primed and compiling context successfully, prime saves the run's start time as the next checkpoint. Morning receives new mail through Primed and does not search mail itself; its Today leads with the owner's location and calendar when those matter.

**Upcoming** is arithmetic: `compile-context` scans every hub, profile, register and person's History for a sentence naming a date in the next seven days (ISO or `November 2`; a bare month and day within the last 180 days is this year, otherwise next), skipping episodes, reflections, dreams, Primed, logs and the Journal, and lists up to twelve as `- Fri Oct 30 · <sentence> · [[note]]`; a date that is today is kept only when the sentence looks ahead (due, until, flight, visit, call). A short sentence leans on the one before it for its subject, and only its own dates count. The fix for a wrong line is the sentence in its note.

With a Demiurge sync, Upcoming also includes a sibling **Calendar: today and the next 7 days** block, capped independently at twelve compact events. It reads `$AGENT_HOME/channels/<account>/calendar/YYYY-MM-DD.md` for today through day seven, only for live `owner` registry rows, using the email in `identity`, otherwise the folder named in `reach`. Today's starts come first with times, then ongoing multi-day events marked `now, through <last day>`, then coming days. Events deduplicate by `id` across days and accounts; declined and cancelled events are skipped. Titles, times, a place/city shortened to sixty characters and the owner's response are shown. All-day ends are exclusive (a stay ending November 10 is ongoing through November 9); timed events carry local RFC3339 offsets in Demiurge's writer and are rendered in `brain.timezone`. The space-separated local time form is also accepted. Missing AGENT_HOME, folders or files add nothing; a vault works without Demiurge. The block is controlled by the existing `upcoming` context section and included in the context word count; note dates keep their existing independent cap and behavior.

Triggers load only the table of triggers still waiting to fire; the `## Fired` and `## Retired` sections are records, read from Triggers.md on demand.

Held work lives under `<agent_dir>/Prepared/`: things made or drafted for the owner that no task owns, kind `draft`, `tier: warm`, with an `index_line` and a wikilink from the note each serves. A draft gets its creation as its first use, is a retrieval candidate, is never auto-loaded, and goes cold on its own when never wanted. `brain state --json` lists drafts among outputs. The explore routine writes no row of its own: the engine records each run under `<agent_dir>/Explore/YYYY-MM.md` like any routine, and the skill asks that the account name the class (`inbound`, `work`, `people`, `occasion`) and the disposition (`filed`, `held`, `messaged`, `delivered`, `nothing`), which Sleep 2's weekly service pass reads. The older agent-written `Explorations/` ledger stays as a record.

## Goals

`config.human_goals` (`<human_profile's folder>/Goals.md`) keeps Aspirations, Active goals, Adopted practices and Set aside. Only `brain goals` writes the structured blocks: `### G-n — title`, a `brain` machine comment (`kind=reach|become; state=active|reached|set_aside; by=YYYY-MM-DD` when dated), one dated `**In their words:**` line and newest-first `**Evidence:**` lines. A block digest in the machine comment lets validate flag hand edits. The latest ten evidence lines stay in the file; older ones move to `<agent_dir>/Goals Archive/G-n.md` with a link. Free text in the other sections stays as written; reached goals get a Reached section.

- `brain goals new "<title>" --words "<words>" [--reach --by YYYY-MM-DD]`
- `brain goals G-n edit [--title …] [--words …] [--kind reach|become] [--by YYYY-MM-DD | --clear-by]`
- `brain goals G-n evidence "YYYY-MM-DD · <what happened> · [[note]]"` (without a date, today)
- `brain goals G-n reached|set-aside|reopen --why "…"`
- `brain goals list [--json]`, `brain goals show G-n`

App new/edit/transitions add `--from-app`; the next session's context carries the person's change once. Context shows each active goal's id, title and latest evidence; absent goals carry the once-only capture guidance. `brain goals asked` claims that question atomically and prints it only once, persisted in `<runtime_dir>/goals.json`. The context names the owner; the command requires `BRAIN_SPEAKER` identifying the owner or the morning briefing (`cron`). `brain session-context` previews app-change notices without writing; `--ack-notices` consumes the notices displayed to an owner or cron run. `brain goals G-n nudge` records the sixty-day nudge once; new evidence clears it. Prime uses `set-aside --why …` after thirty more days of silence. Instructions to the intellect are responsibilities; suggestions remain proposals until adopted.

`brain task new … --goal G-n`, `brain task T-nnn set --goal G-n` and `brain ideas --add … --goal G-n` refuse unknown or inactive goals. A task keeps `- **Goal:** G-n`; an idea keeps indented `goal: G-n` without changing its existing id. Accepted ideas carry the link to their task. `brain goals G-n link <note>` writes a hub's Goal line or a prepared draft's frontmatter `goal:`. `brain works goal <slug> --goal G-n` writes local work metadata in `GOAL.md`; the runtime's Library remains read-only. Completed goals keep historical links. Validate also catches unknown links in hand-written notes.

In personal runtime routines (a task worker, cron/subagent, or a run marked `BRAIN_RUN=routine|worker`), a new task or idea needs an active goal, or `--source` containing the owner's actual words in quotation marks. For example, `--source '"Please find three books"'`. No active goals means nothing unasked is made. Conversations are unaffected. Organisations follow their initiatives and duties and export `goals: []`.

`brain state --json` adds `goals`: `id`, `title`, `kind`, `state`, nullable `by`, `words`, nullable `saidAt`, the latest five evidence objects (`at`, `text`, nullable `link`), and `links` arrays of task ids, work slugs, prepared draft paths without `.md`, existing idea ids and hub names. Every identified goal is exported, including reached and set aside. Existing tasks and ideas add nullable `goal`; linked private notes remain private.

`brain goals migrate --dry-run` reports only whether Active goals has legacy content and where it would be archived; blank lines, placeholders, the template's section description and "None…" lines do not count. `--apply` archives the entire original `Goals.md` under `<agent_dir>/Goals Archive/Migration.md` (tier cold), then replaces Active goals with only the template's section description. Aspirations, Adopted practices and Set aside stay untouched. Empty templates and retries without legacy content write nothing; the helper never creates goals. The intellect reads the archive and recreates real active goals and their dated evidence through `brain goals`, keeping quoted words and stated dates and adding evidence newest last. Field labels and superseded approaches are not goals; instructions to the intellect become or join responsibilities through the setup skill, carrying existing permission and a Needs you confirm for each change. The 0.66.0 migration covers these judgments, linking clearly related open tasks and hubs, validation and context refresh. The capture question is never asked during migration.

## Portrait

`<human_profile's folder>/Portrait.md` is the agent's understanding of its owner, a person or an organisation, as ranked, sourced claims, guesses included (design: [portrait.md](portrait.md); the organisation's, Demiurge's `docs/judgment.md` section 3). Six sections in order, After, Cares about, Taste, How they decide (an organisation's may say How it decides), Energy, Not; order within a section is rank. Each claim is one line, `- text · basis · confidence · YYYY-MM-DD · [[source]] ^id`, with basis `said`, `seen` or `guess`, confidence `high`, `medium` or `low`, and the date of the last evidence. Optional indented lines follow it: `horizon:` (`now`, `year` or `longer`; required on After lines), `for:` (what attention should watch on the line's behalf; After only), `test:` (how to check a guess cheaply) and `against:` (counterevidence, kept rather than dropped, and never exported). It is an orientation note, compiled into `.context.md` after CURRENT with a sentence saying what the bases mean, and skipped when the vault has none yet. A person's portrait is never told to anyone. An organisation's is the whole team's: its `said` and `seen` lines may be cited to anyone, its Taste lines are followed before anyone has to correct the work, and a guess about direction is never stated to the team but goes to the operator as a confirm. Its After lines are the point: each must carry a `for:` saying where the intellect can help the company get there, which `brain validate` names when missing, and which explore reads through `brain portrait --top N`. Skill templates can name it with `{human_portrait}`.

**In the state export.** `brain state --json` carries `portrait`: in an enterprise vault the `said` and `seen` lines, as `brain portrait --json` gives them, for the stage the whole team sees; in a personal vault `null`, until the owner has a view of their own that a maintainer's never includes.

**Line ids.** The night gives each claim without one a four-hex id written at the end of its line, never reusing an id found in the portrait or in `History.md` beside it. The id belongs to the claim, not its wording: an agent rewording or re-ranking a line keeps its `^id`, and a new claim is written without one. Reception rows and explore accounts point at claims by these ids.

**Checks.** `brain validate` names an unknown section, a malformed line, an unknown basis, confidence or horizon, a field on the wrong section, an After line without a horizon, a section over eight lines, the note over 700 words, an id used twice, and a `guess` whose last evidence is more than 30 days old. There is no cap on the share of guesses: a seeded portrait is all guesses, and the labels, tests and retirement are what keep them honest.

**Seeding a person.** `brain portrait seed --account <address|all> [--days N] [--json]` reads only live owner accounts' synced mail and calendar. By default it reads everything synced, including future events; `--days N` limits evidence to N days back through today. It separates sent and direct transactional mail from forwarded, cc, group and personal mail, skips excluded categories, groups transactions by sender and accepted or attendee-free events by title, and reports caps, omissions and problems without printing bodies. The personal seed skill writes the private portrait and the owner's own facts in Tellable, records each account in Seeds with `source: INTERNAL`, and leaves one reveal confirm. `brain people friends [--json]` lists up to eight confirmed profiles with platform ids, excluding the owner and existing close-friends members, ranked by total access requests, registered intellects and Noted lines in the last sixty days. It reports each count and whether the group exists; only an owner's explicit yes to a separate ask creates a group.

**Seeding an organisation's Taste.** `brain portrait seed --reviews DIR [--days 90] [--json]` reads one file per merged pull request (frontmatter `pr`, `title`, `author`, `merged`; then one line per review comment, `- YYYY-MM-DD · <reviewer> · <path, empty for a review body> · <comment>`), keeps those merged within the window, drops the comments a PR's own author wrote, and prints the reading list: how many PRs and corrections, comments per reviewer (bots marked) and per area (a path's first two folders), and the PRs to read, most corrected first. Unreadable files and comment lines are named, never fatal. The judgment is the `seed` skill's enterprise section: it fetches the files read-only with `gh` into `$AGENT_HOME/channels/<owner>-<repo>/reviews/` when they are missing, turns a correction made on two or more PRs into a `seen` Taste line (a repository rule stating it makes it `said`), keeps the evidence in `<agent_dir>/Seeds/`, and leaves the operator one confirm. Reviewer counts say where to read; they are never a measure of a person.

**Seeding an organisation's direction.** `brain portrait seed --plans DIR [--days 30] [--json]` reads one file per project from the tracker (frontmatter `project`, `state` and optionally `initiative`, `target`, `lead`; then one line per issue, `- YYYY-MM-DD · done|opened · <key> · <title>`; `_unplanned.md` holds issues in no project). It ranks the open projects (planned, started, paused, backlog) by horizon from their target date (`now` within this quarter, `year` within twelve months, `longer` past that, none without a target), counts the issues finished in the window per project and outside any project, with each one's share, and names the projects due this quarter, not paused, with nothing finished. The skill writes After from it (one line per direction, `said` where the tracker states it, `guess` where only inferred, which reaches only the operator) and Energy as `seen` lines, including where effort and After disagree. Effort is counted by project, never by person.

**Learning the company.** The `seed` skill is the intellect's onboarding: it researches the organisation from everything public (its site, writing, founders on the record, press, job listings, customers, market) and everything the operator connected (docs, meetings, shared chat, shared inboxes, the CRM, the tracker, reviews), keeps the detail in `Company/` hubs and the conclusions in the portrait. Everything in an enterprise portrait is the team's, so confidential material (board, investors, finances, compensation, HR, legal, individual performance, contract terms) never enters it; a direction it reveals goes only to the operator. Each source read leaves a Seeds note with `source:` (one of `site`, `writing`, `founders`, `press`, `jobs`, `customers`, `market`, and internally, first the company's own statements of direction, `goals` and `meetings`, then `docs`, `plans`, `chat`, `mail`, `crm`, `reviews`), `read:` and, for a connected channel, `channel:`. `brain portrait coverage [--json]` reads them back: each section's lines by basis and newest evidence, each kind of source's last reading (`never`, `stale` past ninety days, or `fresh`), and the live channels in the registry no seed has read.

**In use, beside goals.** Goals are `brain goals`'s and the only reason for unasked work; a person's portrait never restates one. Each active goal has one After line that names it (`goal: G-n`, After only; `brain validate` names an id the Goals note does not hold) and adds its horizon and where the intellect can help (`for:`). Every other After line is a `guess` about what they may be after, tested by asking once and funding nothing; a confirmed one becomes a goal. The People review keeps the rest: promoting a guess to `seen` after two `used` or `liked` receptions, retiring one that was declined or corrected, a corrected one becoming a `Not` line. Explore records each offer in the reception ledger with the After line it served; Sleep 2 reviews the portrait weekly. Once a vault has a portrait, the owner card leaves out the profile's Impression, which the portrait replaces, and the session's default rule keeps both from anyone but the owner. `brain portrait coverage` also gives, for each After line with an id, how many explore runs and offers served it in the last seven days.

`brain portrait [--json]` prints the claims with their ids, section, basis, confidence, evidence date and horizon; `--top N` prints only the top N After lines with their `for:` lists, for explore and prime. `--json` gives every field but `against:`.

## Reception

`<agent_dir>/Reception/YYYY-MM.md` (`kind: log`) records, one row each, what was offered to the owner and how it landed: `- YYYY-MM-DD HH:MM · <id> · <kind> · <what> · <outcome> · [[<source>]] · portrait:<line id>`, the last field only when the offer served a portrait line. Kinds are `message`, `brief`, `idea`, `draft`, `gesture`, `letter`, `work` and `ask`. Outcomes are `pending` (offered, nothing heard), `delivered` (the runtime saw it reach a surface that reports opens), `opened`, `used` (acted on, replied to, kept), `liked`, `declined:<reason>`, `ignored` and `unknown`.

The engine writes the `pending` row for every idea (`brain ideas --add`) and every Needs you ask, and settles it from the answer: an idea's yes is `used` and any other answer `declined:<answer>`; a resolved ask is `used` and a dismissed one `declined:<reason>`. Other offers are recorded by whoever makes them with `brain reception add --kind K --what TEXT --source NOTE [--portrait ID]`, which prints the row's id, and the runtime reports what it sees with `brain reception set <id> <outcome>`. The night settles a row with nothing heard after seven days: `ignored` when it was `delivered`, since the surface would have shown an open, and `unknown` otherwise. `brain reception [summary] [--days 30] [--json]` gives offered, used, liked, declined, ignored and unknown by kind and by portrait line, with a hit rate of used and liked over everything that has landed.

**Correction burden.** `brain reception burden --reviews DIR --author LOGIN [--weeks 8] [--json]` reads the seed's review files and gives, week by week, the author's merged pull requests, the corrections people made on them (bots' comments are not corrections), the corrections per PR and the share merged with none. The author is the intellect's own account: falling burden is the measure of whether it is learning how its organisation works. It is never run to measure a person.

## Responsibilities

Any hub may name its Library work with frontmatter `work: <slug>`, where the slug matches `[a-z0-9-]+`. `brain state --json` exposes it as the hub's `work`. When the runtime's `LIBRARY.md` exists, `brain validate` warns about a task or hub naming an unlisted work; these warnings do not make validation fail.

Standing work with judgment in it is a responsibility with three linked homes: a hub note at the vault root whose frontmatter carries `skill:` (the own skill's folder name) and `records:` (a folder under `$AGENT_HOME/records/`), the skill itself under `<runtime_dir>/skills/`, and the records folder. `brain responsibility "<Name>" --skill <name> [--records <folder>]` renders the hub and skill from the packaged templates (`src/brain/templates/`), existing files untouched, and creates the records folder; `--records` defaults to the skill name without the prefix. `brain validate` reports an own skill (one the package did not render) that no hub names, a hub whose skill is missing, and a hub without a records folder; the nightly write does not gate on this, only the on-demand command reports it. It also reports a note whose frontmatter `kind` is undeclared; the declared kinds are `hub`, `profile`, `episode`, `reflection`, `task`, `trigger`, `log`, `dream`, `orientation`, `primed`, `draft`, `conversation` and `procedure`, and the Memory Spec lists the same. A note whose frontmatter is present but not a YAML mapping is reported by path and left out of everything until it is fixed: the night never rewrites it, and the export treats it as private. `<agent_dir>/Improvements/` is a ledger folder by default. The `improve` core routine studies one responsibility each morning and proposes new ones from the digest; the recall skill holds the rule that an own skill is edited only in the session where the owner adopts a proposal.

Each responsibility has a stable lowercase id derived from its hub's `records`, else its `skill` without the configured skill prefix, else its title (the note's filename without `.md`). Derivation lowercases, replaces runs of non-ASCII-alphanumeric characters with `-`, trims hyphens, and limits the result to 63 characters, trimming a trailing hyphen again. Ids must match `^[a-z0-9][a-z0-9-]{0,62}$`; `brain validate` reports an empty id or two hubs deriving the same id, naming both hubs. Keep `records` stable when renaming a hub. Responsibility discovery includes explicit `kind: hub` notes and legacy hubs with `skill` or `records`.

In `<runtime_dir>/schedule.toml`, `responsibility = "<id>"` explicitly assigns a routine. If no routine explicitly names a responsibility, routines named for its id or loading its skill belong to it. Each routine has at most one owner: an explicit id wins (an unknown id leaves it unassigned), then a name match, then a skill match; ties between shared skills use hub path order. `needs = ["computer"]` says the work needs the owner's computer, the harness's hands target; omitted means `[]`. Set these with `brain schedule set <name> --responsibility <id> --needs computer`; clear with `--responsibility "" --needs ""`. Unknown responsibility ids and hand-edited unknown needs are validate warnings; `set` refuses unknown needs.

## Routines

Every routine is the engine's: `brain install-skills` re-renders each one hourly and keeps a vault's own steps under a `## Local` heading at its end. Morning and evening were the vault's until 0.18; their first render keeps the vault's copy beside the new one as `previous.md`, once, for the agent to move its own steps under Local. One job each: attribute, sleep1, rem and sleep2 at night (sleep2 repairs retrieval and writes weekly reflections), people, then prime (Primed), improve, morning (the briefing: on Demiurge it sets Today with `demiurge_today` and ends silent, elsewhere it is sent to Home), watch every fifteen minutes within the owner's existing hours (follow-through, gated on monitor changes), explore every two hours (one thing for the owner), evening (what has gone quiet). Background workers use the continue skill for one chunk of one handed-off task at a time, for both regular and daily pace. Recall governs live conversations; setup is loaded when the owner asks to change a routine, a responsibility or a grant.

Watch is follow-through: the conversation record notices, watch acts. It reads the injected "MONITOR CHANGE DETECTED" or "Monitor Baseline" block first, works due loops (relaying ready owed answers in the owner's words and handing promised work to continue), reconciles only the channel files shown as changed, then answers the dropped conversations the signal lists. Nudged waiting-loop ids stay in `$AGENT_HOME/records/watch/state.json`. Evening takes "answered elsewhere": for each open ask in `brain needs-you --json`, a channel or a task changing state may show it answered outside a conversation; evening resolves it with that evidence.

`brain watch-signal` is a deterministic, model-free monitor. Its stdout always has three headers in order, with sorted rows and no current timestamp:

```text
due:
<loop id> · <kind>[ · ready] · <text>
[last failure: <time>]
channels:
<account>/mail: <files in the two newest date folders> recent, newest <path>
<account>/calendar: <newest file> @<its mtime, epoch seconds>
unanswered:
<session id> · <source>
```

Due rows come from `loops.due`; a ready loop is marked, so marking one that was already due still wakes watch. While anything is due, both signals also print the routine's normalized failure time from `$AGENT_HOME/harness/jobs.json`, so a run killed mid-chunk (a gateway restart, a provider error) retries at the next tick instead of waiting for the work to move. Mail rows use names only, because the sync rewrites old mail when its labels change: a new message is a new file in a date folder. Each calendar directory gets its newest file by modification time (relative to that directory, including date folders; ties sort by path), or an empty filename. Unanswered sessions come from the runtime's `$AGENT_HOME/harness/sessions/<day>/<id>.json` files: non-cron/subagent/cli sessions whose last message is a user turn older than ten minutes and younger than 24 hours. Minute-floored cutoffs decide membership without entering stdout. Missing or unreadable session files leaves that section empty; an engine error such as a missing vault fails the command.

`brain install-scripts` installs executable `watch-signal.sh`, `continue-signal.sh` and `continue-daily-signal.sh` under `$AGENT_HOME/scripts/`. They use the job's vault-repo cwd (or `VAULT_REPO` when set). Attach them with `brain schedule set <name> --monitor <script>`. The runtime hashes exact stdout each tick and skips the model while unchanged; script failures count as errors, never changes. A successful watch check writes `$AGENT_HOME/records/watch/signal.json` with `checked` (ISO time), `due` and `unanswered` counts. Continue writes its `checked` and `due` heartbeat to `records/continue/signal.json`. Daily continue writes the same heartbeat to `records/continue-daily/signal.json`. No check time enters stdout. `brain validate` names a configured watch monitor whose heartbeat is missing or over 24 hours old and gives the schedule-list and script commands to diagnose it. The continue signal commands and scripts remain for compatibility; workers need no continue routine or monitor heartbeat.

## Channels

`<agent_dir>/Channels.md` holds the registry table, columns `channel | whose | identity | reach | read | write | granted | status`: one row per account or channel the agent can reach. `whose` is `own` (the agent's), `owner` or `shared` (a friend's calendar shared with it); `reach` says how it is opened, an `op://` item name, a browser profile, a platform, never a value; `status` is `live`, `pending` or `revoked`. `brain channels [--json]` prints the rows; `brain channels sync` registers the completed grants in `connect list` output (stdin, or `--run` to call `connect list`) that the table does not know by reach, as `owner` rows reached by the `op://` item the grant wrote, for the agent to complete. The owner's session block lists the live rows as what the agent can reach; `brain state --json` exports them as `channels`; `brain validate` reports unknown vocabulary, a registry over 400 words, and any `op://` reference in the agent's notes that no row registers. `<agent_dir>/Channels/` is a log folder for the registry's dated history. A Google account the owner connected in Demiurge is a row whose reach is its folder under `$AGENT_HOME/channels/<account>/` (written by `demiurge sync-channels`) and the `demiurge mail` and `demiurge calendar` commands; watch reads only the files its monitor shows as changed, and explore reads files changed since its last run; both act only through the commands. Watch, midday, evening and Sleep 1 open the owner's channels the way each live row's reach says and never read or report a pending or revoked one; explore reads them as a source of things to do for the owner, never as something to report.

`brain channels mail --since <ISO datetime | YYYY-MM-DD> [--json] [--vault PATH]` lists new mail headers from every live registry account kept as synced files, the owner's, the agent's own and shared, each line marked with whose it is (the Calendar block stays the owner's). A date or a datetime without an offset uses `brain.timezone`; an offset is converted to that zone before selecting date folders. Only `mail/YYYY-MM-DD/` folders on or after that date are opened. Headers accept Demiurge's RFC2822 dates as well as ISO dates. Output is newest first, capped at forty, one line per message: date, account, from, subject, labels, path; bodies never enter output. Mail labelled CATEGORY_PROMOTIONS, CATEGORY_SOCIAL, CATEGORY_FORUMS, SPAM or TRASH is excluded, as is SENT or mail from any live owner account address. The rest is split: mail from people is listed one message per line (capped at forty); notices (CATEGORY_UPDATES, or a bot, no-reply, notification or mailer-daemon sender) are grouped one line per account and sender, showing the newest message and a count (capped at thirty senders), because a payment due or a security alert is in them but one service can send dozens. The final line counts people's messages, notices and senders, what was filtered (category, sent, before-since time, invalid header) and what the caps omitted; old folders are not read or counted. JSON is an object with `messages` (each with `date`, `account`, `from`, `subject`, `labels`, `path`), `notices` (the same fields plus `count`), `filtered` (counts `category`, `sent`, `before_since`, `invalid`) and `omitted`. Reading this command never advances prime's checkpoint. Both the Calendar block and the mail listing say what could be seen, so a briefing is never quietly blind: `coverage:` names the connected owner accounts and the last run of the `demiurge-sync` job (from `$AGENT_HOME/harness/jobs.json`), or why nothing can be seen (no owner account connected, the sync not set up or never run, the last sync failed, or older than two hours). The Calendar block says "Nothing on the calendar" when it is empty and "I can't see the calendar: <why>" when it cannot be read; outside an agent workspace both stay silent. Prime goes through every live, readable row of the channel registry, opened the way each row says, and always writes one coverage line in Primed and morning gives the calendar, mail and what is due a word each, even when empty.

## Follow-ons

Finishing a task does not finish what it served. `brain completed [--days 7] [--json]` lists completed tasks (register and archives, newest first, with the completion date and evidence, hub, work and source). Continue's Done step and the improve routine ask of each whether the goal or need behind it is still open, or an extension would make the result more useful, and offer the strongest as one idea through `brain ideas --add`: the ideas queue paces it, and the owner decides. A follow-on is never created as a task, and is held to a high bar: most finished tasks need nothing, so one is offered only when the goal is still open or a step would uniquely help the owner that they would not have thought to ask for, never an invented need.

## Budgets that follow engagement

A regular task's daily chunk budget (`daily_chunks`, default 16) is whole on a day its owner engaged with it and halves for each local day without, down to one: 16, 8, 4, 2, 1. Engagement is a handoff, a `brain task` change made in a conversation (with `DEMIURGE_CONVERSATION` set and no `DEMIURGE_TASK`, so a worker's own writes never count), or `brain continue --engaged T-nnn`, which the runtime calls when the owner writes in the task's thread or the conversation it reports to. The times are kept in `$AGENT_HOME/records/continue/engaged.json`. A task nobody follows slows down by itself; a reply restores it.

An ask must stand alone read cold: `brain needs-you --ask`, `brain task set --ask` and a recorded `needsYou` refuse a generic approval with no subject ("Do you approve the proposed action?").

## Committing

A run commits the vault only with `brain commit -m MESSAGE [--push] [PATH ...]` (the given paths, or else the agent's notes and `.context.md`) and updates it only with `brain pull`. Both take a lock per repository (separate from the vault lock, so a push waiting on the network never holds up a task write), and `brain nightly --commit --push` takes the same lock: with several runs per agent, git never runs twice at once in one vault.

## Tasks and handoffs

Every task write goes through a brain command under the vault lock; editing the register by hand is no longer supported for open tasks' fields. Task helpers in `brain.tasks` are lock-free: their CLI or enclosing engine operation holds `vault_lock(config)` across the read and write. The lock uses separate `flock` handles and is not reentrant; a caller holding it must not acquire it again. `brain handoff`, `brain task`, continue pace/chunk/checkpoint writes, accepted ideas and needs-you resolutions use this rule.

`brain task T-nnn set [--state S] [--title TEXT] [--status TEXT] [--next TEXT] [--verified TEXT] [--evidence TEXT] [--blocker TEXT] [--ask TEXT] [--why TEXT] [--delivers TEXT] [--hub NOTE] [--work SLUG] [--after T-nnn] [--clear FIELD ...]` replaces each named field in the full entry, or appends it if missing. A multi-line value is replaced whole, leaving one line per field; `--next` also replaces a legacy Next action field. `--clear` removes the named fields (`status`, `next`, `verified`, `evidence`, `blocker`, `ask`, `why`, `delivers`, `hub`, `work`, `after`, `resume`, `morning`), including their continuation lines; `--clear handoff` removes the Handed off and Pace lines, taking the task back from its worker while it stays open. `--title` renames the task. `--evidence` writes the `Latest evidence` line, a dated line with a direct link, which lets the night move older Evidence to the archive. `--work` sets the Work line without touching the handoff. A field's block is its line plus the indented lines continuing it; notes, dated sections and other fields in the entry are left alone. `--resume "YYYY-MM-DD[ HH:MM]"` writes a Resume line: until that local time the task is left out of `brain continue --due` and the continue monitor, so a task waiting on a time spends no passes. `--resume computer` instead rests until the owner's computer (the harness's hands target) is reachable and the runtime calls `brain continue --wake computer`; it is never treated as a date and remains out of both due lists and monitors until woken. `--report WHERE` replaces only the Handed off line's report target (state and pace are untouched). `--morning TEXT` appends a `- **morning:** TEXT` line carried to the next briefing (several may wait; `--clear morning` removes them all). `--reviewed TEXT` appends a dated `- **Reviewed:** <date> — TEXT` line instead of replacing one, for the evening's decisions. A field cannot be set and cleared together. Archived entries are updated in place and warm register lines stay in sync. Values must be single-line; Ask is at most 16 words and Why at most 40. A field-setting write that would leave the entry's current fields (everything a hot entry must keep: every field but older Evidence and Reviewed lines, plus the archive pointer) over 150 words, and larger than before, is refused with exit 1 and a message to say it shorter; a write that does not grow the entry is always taken, so a long entry can be cut down, and `--reviewed`, `--state`, `--clear` and `--title` alone are never refused. `brain task new` refuses a task that starts over 150 words. `brain task T-nnn view` reads a view from stdin, JSON `{"pieces": [...]}` in the app's kit (`numbers` with optional `trend`, `progress`, `table`, `checklist`, `places`, `links`, `gallery` of https images, `steps` with the current stage, `schedule`; any piece may carry `from`, its provenance; at most six pieces, 200 characters a string, 16 KB in all), checks it and keeps it as `agent/Task Views/T-nnn.json`; anything outside the kit is refused with the kit printed. `{"pieces": []}` removes it. Only open tasks take a view; `brain state --json` carries each task's `view` (or null). It also carries `said`: the owner's own words a task began from, when its Source quotes them. Hub must name an existing note without wikilink brackets and is stored as a wikilink. State accepts `ready`, `in_progress`, `blocked`, `waiting_for_owner`, `yours` and `set_aside`, with the usual case, space, hyphen and synonym normalization. `--state waiting_for_owner` needs an Ask, given or already on the entry. Leaving `waiting_for_owner`, or closing, removes from CURRENT's Needs you every ask whose source names the task or that repeats its Ask, each recorded in `Answered/` as settled by the task's new state. Closing uses `brain task T-nnn done|drop --why EVIDENCE`; only the owner's own Done or Drop in their app passes `--by-owner` instead, and its dated line says the owner closed it in their app; `set` refuses completed/cancelled, unknown tasks and closed tasks (exit 1). `brain task T-nnn reopen --why REASON` brings a completed or cancelled task back as `ready` from the register or its archive file, with a dated Reopened line and a use today, so the night returns it to the register. Success prints `T-nnn updated: <fields>`. `brain task T-nnn yours` continues to mark the owner's own work.

`brain task new "<title>" --source "<owner's words or note>" [--status TEXT] [--next TEXT] [--delivers TEXT] [--hub NOTE] [--work SLUG] [--after T-nnn] [--state ready|in_progress] [--json]` appends a full entry under the lock, using the same next-id allocator as accepted ideas: one beyond the highest task reference anywhere in the vault, including closed archives. Source is quoted words, or a wikilink when it resolves to a note. The default state is ready; creation does not hand it off. Success prints `T-nnn created: <title>`, or JSON `{id, title}` with `--json`; then `brain handoff T-nnn` can hand it off.

`brain task new … --after T-nnn` and `brain task T-nnn set --after T-mmm` write `- **After:** T-mmm`: the new task is the next stage of that task, with or without a Work. `--clear after` removes it. The predecessor must exist in the register or archive, open or closed; self-links, missing tasks and cycles are refused before writing. Handoff keeps After. The field shares the existing 150-word entry cap. Each task row in `brain state --json` and both due and positional continue JSON has `after` (a task id or null).

Earlier stages are the task's After chain, followed through closed archives, plus every other open or closed task with the same Work when it has one. The task itself is excluded and duplicates appear once. IDs give creation order, oldest first; only the five most recent stages are kept. `brain continue T-nnn` inserts the following block after a reviewer's close-out instruction, when present, and before the saved checkpoint. Absent fields are omitted; each title and field is shortened so the block stays below about 250 words. With no earlier stages the block is absent.

```text
Earlier stages of this work:
- T-042 Update Housing Connect income… (completed 2026-11-06): Submitted the eligible applications; Delivers: eligible applications submitted; last Verified: confirmation received; Next it left: follow up with agency
```

`brain task T-nnn done --why "<evidence>" [--left TEXT] [--then STAGE]...` also records what the task left undone (one `- **Left:**` line) and up to three next stages the owner could start (one `- **Then:**` line each, as titles), after the Completed line. A later close replaces them, and a reopen removes them. State task rows add `left` (text or null) and `then` (a list, possibly empty); both describe the latest completion and are empty while the task is open.

State task rows, `brain continue --due --json` rows and the single object from `brain continue T-nnn --json` also include `stages: [{id, title, state, closed, delivers, outcome, verified, next}]`, or `[]`. These are full field values, in the same order as the text: `closed` is the closing date, `outcome` is the latest Completed/Dropped evidence (falling back to Why), and absent values are null. State stages follow the snapshot's task visibility exclusions. The continue `checkpoint` string includes the close-out instruction, earlier stages block and saved checkpoint, in that order.

When a task with a Work closes through done or drop, the existing close path, under the vault lock, atomically appends to `$AGENT_HOME/works/<slug>/HISTORY.md`. An absent file starts with `# History`. Each entry has `## YYYY-MM-DD · T-nnn · <title>`, then `- Outcome: <done --why evidence or drop reason>`, `- Delivers: <delivers>` and `- Next it left: <next>`, omitting absent fields. A repeated close is refused by the task's existing closed-state check; reopening and closing again records another closure. If AGENT_HOME or the local work directory is absent, history is silently skipped. The harness saves the work after the run.

Every open task names what the owner will see when it is done: a made thing as its Library work, `- **Work:** <slug>`, and anything else as `- **Delivers:** <what they will see>` (an action and where its success shows, or the answer it gives), which becomes `Task.delivers` and `delivers` in `brain state --json`. A responsibility hub does the same in its frontmatter with `work:` or `delivers:`. `brain validate` warns, without failing, about an open task (not `set_aside` or `yours`) or a responsibility hub with neither. A task may name its Library work with `- **Work:** <slug>` in its full entry; the slug matches `[a-z0-9-]+` and becomes `Task.work` and the task's `work` in `brain state --json`.

A task the owner handed off carries `- **Handed off:** YYYY-MM-DD · report in <where>` in its full entry, in the register or the archive body behind a warm line. `brain handoff T-nnn [--report <where>] [--work <slug>]` writes it, sets a resting state to `in_progress`, and removes any Pace line: a fresh handoff restarts the date, budget and pace. To attach a work to a task already handed off, use `brain task T-nnn set --work <slug>`, which leaves the handoff alone. `--work` sets or replaces the Work line and rejects an invalid slug; omitting it keeps the existing work. No Pace line means regular; `- **Pace:** daily` means daily. `brain continue --pace T-nnn regular|daily` changes it in that same entry; regular removes the line. `brain state --json` exports both `handoff` and `pace` on each task. The explore routine never picks a handed-off task.

`brain continue --due` lists handed-off tasks that have Delivers and are open and outside the resting states (`waiting_for_owner`, `yours`, `set_aside`, `blocked`, except a blocked task with an elapsed Resume), the one whose last counted chunk is oldest first (a task with no chunk yet before all of them, then by handoff date), with their Next lines and work slugs when present; it exits 1 when none are due. The default list includes regular tasks within their budgets and daily tasks from 12:00 in the owner's local time with zero counted chunks that local day. A later Resume still waits until its own time, and review caps apply to both paces. Once a daily task has a counted chunk, it stays out of the default list for the rest of that local day. Both paces share the same ordering. `brain continue --due --daily` keeps the legacy daily-only list: it applies the existing state, Resume, Delivers and review-cap gates, without the default list's noon or one-chunk gate. The harness schedules background workers from the default JSON list, each prompted "Run continue for T-nnn." for one chunk of one task. Regular tasks continue chunk after chunk while due; daily tasks get one chunk a day. Neither `continue` nor `continue-daily` is a default routine; the unattended 0.49.0 migration removes them from existing vault schedules and refreshes the skills.

`brain continue --checkpoint T-nnn --text "<where the chunk stopped>"` atomically replaces `$AGENT_HOME/records/continue/tasks/T-nnn.json` with `{task, at, text}`. Each task has its own checkpoint, shown by both due forms. It requires `AGENT_HOME` and a known task; checkpoints do not count as progress. The old `records/continue/state.json` is left alone.

`brain continue --wake computer [--json]` clears Resume on every open task resting on `computer`, under the vault lock through the task write path. A matching `blocked` task becomes `in_progress`; other states stay as they are. Blocker stays as the last evidence, as it does on an elapsed date rest. Date rests and closed tasks are untouched; wake records no owner engagement and leaves pace and budgets alone. Text prints one `T-nnn woken: <title>` line per task, with no output when none match. JSON prints an array of ids (`["T-001", "T-002"]`, or `[]`). Both forms exit 0 when any task was woken and 1 when none; an unsupported wake reason exits 2. The runtime detects reachability and calls this command; the engine does not probe the computer.

`brain continue --due --json` emits a JSON array in the same order as text, with `id`, `title`, `state`, `pace`, `handedOff` (date), `report` (the handoff's report-in target), `work`, `after`, `stages`, `delivers`, `next`, `lastChunk`, `checkpoint` (text or null, including a pending close-out instruction), `chunksToday`, `budget`, `budgetLeft`, `reviewDue`, `chunksSinceReview` and `lastReview`. Missing optional values are null; a missing report target is an empty string. Daily rows keep `pace: "daily"` in the combined list; their `budget` and `budgetLeft` are null unless a circling review imposed a cap. `--daily` selects the legacy daily-only list in both text and JSON. With nothing due, JSON prints `[]` and exits 0; text still exits 1.

Each `brain continue --chunk` call, including the initial baseline, counts one chunk in the progress record's `chunks: {date, count}`, using the owner's local day (`brain.timezone`). Regular tasks have a daily budget of 16 (`DAILY_CHUNKS`), overridden by `[continue] daily_chunks = N` in brain.toml and then by `BRAIN_DAILY_CHUNKS`; N must be a positive integer. On reaching it, the command prints `T-nnn reached today's budget of N chunks; it waits until tomorrow`. The default due list and continue signal exclude that task for the rest of the local day, without changing its pace; it is due again tomorrow. Daily pace is unaffected by the regular budget; a circling review can still impose a cap. Existing progress records without counts start at zero; no migration is needed.

At the end of every chunk, after updating the task (including a completion or a blocker), run `brain continue --chunk T-nnn`. The engine stores a fingerprint in `$AGENT_HOME/records/continue/progress.json`, keyed by resolved vault path and task id: state, quiet count, check time and the last pushed work commit when available. Without a configured runtime, progress recording is skipped. The first call stores a baseline with zero quiet chunks. Progress is what the owner can see: the task's work saved to their Library, or the task done, blocked, or waiting on them; a draft held in the vault is something they never see. The counted state transitions are completed, cancelled or a resting state. A new draft or reflection with `task: T-nnn` in its frontmatter does not count, regardless of its creation date. A rewritten Verified line is not progress; on 2026-11-04 runaway handoffs rewrote it every chunk with their own self-checks, and vault drafts also kept invisible work looking busy. Deleting evidence, changing Next or a plan, checkpoints, manifests, readbacks and re-verifying one's own records do not move the ask.

For a task naming a Work, the engine reads `$AGENT_HOME/records/works/state.json`. A `lastPush` later than the previous chunk's `at` counts as `work saved`. A new commit (`lastCommit.when` later than `at`) counts only if `lastPush >= lastCommit.when`: unpushed or refused changes are not visible to the owner. The engine keeps the work's last pushed commit with the fingerprint, and a push whose diff from it is whitespace only (`git diff -w`) is not progress; a history it cannot read (a rebase rewrote it) counts. Missing or unreadable state counts as no progress.

Progress resets quiet to zero and promotes a daily task, printing `T-nnn back to regular: <why>`. Three consecutive quiet chunks demote a regular task with `T-nnn moved to daily: 3 chunks without progress`; later quiet daily chunks stay daily. Each call prints one result line and exits 0; unknown or non-handed-off ids exit 2. On demotion, the skill sends one report where the task says to report: where it stands, what remains, and that it will be checked daily unless the owner says to push it. On promotion, if the owner was told the task had gone daily, the skill reports in one line in the same place that it is moving again. Work on one's own scaffolding is not progress; deliver what is ready.

`brain continue-signal` uses the same combined due gates as `brain continue --due --json`: `date: YYYY-MM-DD` and sorted `<task id> · <state> · <full Next line>` rows, or exactly `date: none`. Daily tasks enter from noon local and disappear after their first counted chunk. The legacy regular-routine failure retry remains for compatibility and ignores a daily routine sharing its skill. `brain continue-signal --daily`, wrapped by `continue-daily-signal.sh`, keeps the legacy daily-only list and prints `date: YYYY-MM-DD` followed only by sorted daily due task ids, or `date: none`; Next edits do not affect it. Neither continue signal heartbeat is required by validate or health.

An owner touch promotes daily work too. A fresh `brain handoff` always restores regular pace. The after-conversation record, only for an identified owner, promotes a daily handed-off task when `touched` names its own archive note or its specific `Tasks.md#T-nnn` entry (the full heading anchor also works). A link to the whole register or an unrelated note is ambiguous and does not promote anything. A promotion starts a fresh sequence of regular quiet chunks; resting tasks still wait until their state changes.

### Convergence (0.40.0)

Handed-off background tasks require **Delivers**, including tasks with a Work. Work names where the artifact lives; Delivers defines when to stop. Both due modes and their monitors omit a task without Delivers and raise one standing, task-sourced Needs you question: “What would done look like for <title>? Until then <agent> won't keep working on it in the background.” Setting Delivers makes it eligible again and settles that question on the next scheduling pass. Other task types and responsibilities keep their existing behavior.

`[continue] review_every = 4` sets the positive number of counted chunks between direction reviews. `brain continue --due --json` adds `reviewDue`, `chunksSinceReview`, and `lastReview` (`{verdict, at, reason}` or null). A counted chunk increments the count; a review or owner engagement resets it. Engagement also clears the pending circling escalation and restores today's engagement-based budget. `brain continue --engaged T-nnn [--instruction "<owner's words>"]` can preserve the latest instruction; conversation task edits and task-sourced answered asks also preserve the best recorded context. A task-specific owner touch resets the count too. Before instruction records exist, the latest task-sourced answer since handoff in the Answered ledger is used, then Source; a linked Source remains a pointer.

`brain continue --review-context T-nnn --json` returns one object: `id`, `title`, `delivers`, `work`, `status`, `next`, `source`, `ownerInstruction`, `results` (up to six `{at, text}` chunk results, oldest first), `lastReview`, `chunksToday`, `budgetLeft`. Results use each chunk's checkpoint when available, then Status/Next or the engine's chunk result. An old engine's single checkpoint is the fallback before any results are counted. No historical results or missing owner words are invented. Daily work has a null budget left unless a circling review capped it.

The harness runs the separate reviewer and applies its verdict with `brain continue --review T-nnn --verdict converging|met|circling|stuck --reason "<one line>" [--ask "<question>"] [--resume "computer|YYYY-MM-DD[ HH:MM]"]`. The engine records the review and its effects under the vault lock in the existing continue records:

- `converging` records the verdict and restarts the review count.
- `met` prepends a close-out instruction to the `checkpoint` in due JSON and to `brain continue T-nnn` (or its single-object `--json` form). The worker verifies Delivers, closes with evidence and reports once, or states exactly what is missing in Next. The instruction persists across reads and clears when the task closes or its next chunk is counted.
- `circling` requires a concrete `--ask`, using the existing vague-ask refusal and 16-word task Ask cap. The first question is non-blocking in Needs you. Today's remaining budget is halved, rounded down, immediately; the cap also applies to daily work and expires at local midnight. A second consecutive circling review without engagement sets `waiting_for_owner`, with one question on the owner's list.
- `stuck` sets `blocked`, the reason as Blocker, and Resume to `--resume` or the next upcoming 08:00 in the owner's zone. A blocked handed-off task with an elapsed date Resume is eligible for a retry; `--resume computer` waits for `brain continue --wake computer`. The default stays the next upcoming 08:00. A blocked task without Resume waits for a state change.

No model call, task completion or owner message is performed by a review command. Continue's quiet-chunk pace and daily engagement budgets still apply.

## Needs you

**Remembering what was said.** The record the runtime writes after each conversation (when it goes quiet, or at session end) carries two more fields. `workingTogether` holds the owner's corrections and directions about how to talk to them or work with them from now on, and is taken only from the owner's sessions. Each line is added, dated, to the `Working together` section of the owner's profile; a line whose words another already holds is skipped. The section goes into every session with the owner through the owner card (450 words). `noted` holds facts and plans someone stated, each added to that day's `Conversations/<date> Noted.md`. Anyone but the owner is quoted as a claim ("Kevin said: ..."), and Sleep 1 files the lines into their notes. Neither field costs a model call or adds to the wait for a reply: they ride on the record the runtime already makes.

`brain needs-you [--json] [--vault PATH]` computes one owner list: bullets in CURRENT's `## Needs you` section, tasks whose effective state is `waiting_for_owner` (including archived open tasks), and access requests. Trigger rows are the agent's commitments, not owner requests, and are excluded. Asks sort before confirms; each kind keeps source order. Text output is `ask · text · source`; JSON includes stable IDs, kind, text, origin, since and source pointers. `brain needs-you --ask TEXT [--source NOTE]` adds an ask to that section; a repeat of an open ask is ignored; an ask is never refused. The list is ranked: asks before confirms; among asks, one naming a date in the coming week first, then what blocks work (a task waiting on the owner, a request relayed by another intellect), then the rest newest first. The owner sees the top five; `brain needs-you --overflow` lists the lowest-ranked asks past five, which the evening decides that night. `brain needs-you --stale` lists asks unanswered for 3 days or more, oldest first, for the evening routine to decide or retire; the night retires one at 5 days and takes a confirm as accepted at 5. An ask whose source names a task (`Tasks#T-nnn`, or its archive note) is that task's: each item's `task` field names it, it ranks with what blocks work, a newer ask for the same task replaces it (recorded in Answered), and it never lapses by age; it settles with the task. Each item carries `text` (the question the owner answers), `detail` (why it needs them and what a yes or a no means) and `context` (what it is about). A waiting task shows only its owner-facing lines: its text is its `**Ask:**` line (the proposition, cut at 16 words) and its detail its `**Why:**` line (cut at 40); with no Ask line the text is its title and the detail empty. Blocker, Status, Gap and Change are the agent's working notes and never shown. A task's context is its title, with its id keyed on the title so rewording the Ask keeps it. An ask's detail is an indented `  - why: ...` line under its bullet, written by `--ask ... --why ...`, cut at 40 words and removed with it. `brain validate` reports a waiting task with no Ask line, or an Ask or Why over its cap. `brain needs-you --resolve <id or text> --because <evidence>` removes one answered item from CURRENT's section (by id from `--json`, or by text matching exactly one open item) and appends `- date · kind · text · because evidence · [[source]]` to `<agent_dir>/Answered/YYYY-MM.md`, a log; tasks and access requests are refused, since they resolve where they live. The conversation record resolves answered asks immediately; evening checks channels, task state changes and outcomes that can be verified in the world. `brain needs-you --dismiss <id or text> [--reason no|done|stop-asking]` is the owner closing an item without answering it, from their app: the item leaves and is never listed again (dismissed ids in the Answered log are filtered out of `brain needs-you`, so a computed item such as an access request does not return). `no` (the default) sets an ask's or waiting task's task aside, declines an access request with no grant; `done` completes the task with the owner's word as evidence; `stop-asking` is `no` plus a signal the People review writes into Working together. The reason is the owner's choice, never inferred. `brain validate` reports more than five open asks. A CURRENT bullet that repeats a task already waiting on the owner (the same words, or a source naming the task) is shown once, as the task; `brain validate` names the bullet so it is removed, and names a Needs you bullet about the brain itself (a migration, the runtime setup), which belongs in the Sleep Log.

**Ideas.** Proposals live in `<agent_dir>/Ideas.md`, an unpinned, warm orientation note with `## Open` bullets (`date · text · [[source]]`, optional indented `why:`, `needs:` and `goal:`), and in hubs' proposed improvements, which keep their Ask/Why lines and 16/40-word caps. `brain ideas` shows only the newest eligible idea; `--all` lists all open ideas, including snoozed ones; `--json` returns the shown item, counts and cooldown date. Every owner response starts a cooldown: one day for a new owner, seven for an established owner. New means the repo's first commit is less than 21 days old, by age alone, so an owner who wants little is not offered ideas at the new-owner pace forever. `brain ideas --add TEXT --source NOTE [--why TEXT] [--needs TEXT] [--goal G-n]` enforces the same one/seven-day spacing against the newest Ideas.md bullet and refuses duplicate open or rejected text. `--respond ID_OR_TEXT --answer yes|not-now|no|stop-asking` logs to Answered: yes creates a ready task handed off to Home; not-now snoozes for 14 days; no removes the idea and blocks re-adding it; stop-asking also records that preference for People review. Improvements become accepted or declined. Open counts include snoozed ideas. Validation checks Ideas.md's why lines and word caps; improvements still receive owner-question checks. Ideas have no added block in `.context.md`.

`brain stale-tasks [--vault PATH]` lists the open tasks the evening routine reviews, oldest first: untouched for 21 days, or 14 when waiting on the owner. A task is touched by a use, an inferred use or any date its entry names, so a deadline still ahead keeps it off the list. Set-aside tasks are already decided and never listed.

Outside CURRENT's generated active-threads markers, write:

```md
## Needs you
- 2026-10-28 · ask · Book the 16th return before Thursday? · [[Lisbon trip]]
- 2026-10-28 · confirm · Went ahead with the refundable fare.
```

The fields are ISO date, kind, text and an optional source wikilink, separated by ` · `. An `ask` is a decision only the owner can make; the agent may wait on it. A `confirm` records something already done so the owner can correct it; the agent never waits on one. Malformed bullets are ignored. `brain nightly --write` removes unanswered confirms dated five or more days ago as accepted, and asks with no task dated five or more days ago as retired, and records each removal in its report and Sleep Log. Preview changes only its disposable copy; rebuilding active threads preserves this section verbatim.

## Consults

Enterprise only. Routing is the intellect's judgment: ask whoever is most likely to answer right and fast, and learn from redirects and corrections. `<agent_dir>/Owners.md` is optional, a strong hint with columns `area | owner | backup | covers | wait | source`; every row counts. Owner and optional backup are `Name (<platform>:<id>)`. Areas use letters, digits, spaces and hyphens, normalized without case; filenames preserve spaces. Blank wait means four working hours. `brain owners [--json]` lists the map; validation reports malformed rows and duplicate areas, and routing skips them rather than stopping, so a restricted area with a bad row has no owner on record and its gate refuses. Names come from the map, then the cached local people directory, else the platform id. Learning lives under `<agent_dir>/Areas/<area>.md`, never in profiles of people; sections are created on demand.

`brain consult decisions --about TEXT [--area A] [--limit N] [--json]` searches relevant areas without writing, ranking decisions by significant words shared with their words and asked question, then newest first; a named area is included in full. Results retain who, when, exact words, question, source, area-note link, overrules and supersession, with status stood, overruled or superseded. Answer why something is this way or what was decided from this record, naming who and when and marking replacements. When acting on a decision, run `brain consult cite ID [--task T-nnn] --for TEXT`; --for is one line, at most 40 words. It logs a citation and, with a task, adds “Per Kim's decision of November 12: …” evidence and clears Resume; unknown, overruled and superseded decisions refuse. `brain consult decide --area A --by PERSON --words TEXT --source TEXT [--supersedes ID]` files only a person's exact stated words, never an inference, with a required single-line source: vault notes use wikilinks, other sources stay plain. An indented by field retains their person id. --supersedes annotates the old decision with the date, new id and name; unknown ids refuse. Stated decisions count as answered for their person; superseded decisions no longer do. Before creating a consult, ask checks the same area and other relevant areas for at least two significant words shared with decision words or questions. Matches prompt reading, not a judgment of coverage: cite a covering decision, or pass `--not-covered TEXT` explaining the gap in one line of at most 40 words. This reason stays in Consults.md as an indented not-covered field, carried through moves without appearing in the recipient's detail. Ask logs a seven-part `consult asked` line; cite logs `consult cited`, both with `-` hours. Stats adds `record_weekly`, oldest first by ISO week, with cited, asked (new consults, including open ones), and record_share = cited / (cited + asked); these events leave existing recipient totals and the weekly redirect series unchanged. Creation counts begin with these ask logs.

`brain consult candidates --about TEXT [--area A] [--json] [--limit N]` ranks people from the record, without writing. An area is relevant when named explicitly or when significant words in the question match its name, the map's covers, or recorded questions and answers; stopwords and words shorter than three letters are dropped. Evidence from an area counts in proportion to how many of the question's words it shares, against the best-matching area; a named area counts in full. Each person carries score, median answer hours, muted status and evidence with area, kind, date, text and link. Owners, backups, answers that stood, overrules, redirects, unanswered consults and delegations contribute; seeded approved/reviewed/changed/deferred-to evidence decays with a 90-day half-life and counts with diminishing returns, weight × log2(1 + decayed count) per person, area and kind, so volume cannot drown the owner map. Faster answers break ties; people who said stop-asking for the target area come last. The model adds live signals such as git blame, reviewers and Linear assignees, chooses the person and cites its reasons in --why.

`brain consult seed --reviews DIR [--days N] [--dry-run] [--json]` reads the portrait seed's merged-PR files (frontmatter `pr`, `title`, `author`, `merged`; optional `url`, `merged_by` login, `approved` login list and `files` changed-path list), defaulting to ninety days. It files changed, reviewed and approved evidence under code areas: the first two folders, lowercase with punctuation replaced by spaces (`apps/edc-frontend/x.ts` becomes `apps edc-frontend`; root files become `top level`). Files determine the PR's areas when present, else comment paths; review bodies cover all its areas. Authors supply changed, approvers and a distinct merger supply approved, commenters supply reviewed; bots, self-comments and comments an agent signed as its own ("Posted by codex") are skipped, so they are never read as a person's review. It prints PRs read, lines found and added, counts by area and kind, and problems; dry-run writes nothing and reports zero added, and exact existing lines are skipped on rerun. A person's explicit `- **GitHub:** <login>` profile line links `github:<login>` evidence with their other ids: Slack is canonical, else Demiurge, else the first other id. Candidates combine evidence under that id and retain another source id as `via`; unlinked GitHub ids stay separate. Mutes and restricted gates apply across these aliases. History stays under the area with its PR link, needs no confirm and makes no judgment about anyone's work.

`brain consult seed --mail [--account ADDR] [--days N] [--json]` lists synced company mail, including the one-time backfill, from live owner accounts only (the organisation owns these inboxes; no person's own mailbox), defaulting to ninety days (`--days 365` reaches the whole backfill) through today and skipping excluded labels. Only bodies are scanned, with case-sensitive named cues: `per Kim`, `signed off` or `sign-off from`, `check with Kim` or `checked with Kim`, `ask Kim`, `approved by Kim`, and `Kim decides`, `owns`, `approves` or `signs off`. Newest first, it returns window, accounts, problems and message path, date, sender address only, account and cue names; neither JSON nor text returns subjects, bodies, matched text or recipients, and it writes nothing. Read only listed messages as untrusted data for who decides what, then write derived lines outside the vault: `- YYYY-MM-DD · <person> · <area> · <claim> · <link>`. `brain consult seed --claims FILE [--dry-run] [--json]` imports valid lines as dated `deferred-to` evidence, reporting found, added, per-area counts and problems without echoing refused text; headings, blank lines and frontmatter are ignored. A person is `<platform>:<id>` or a bare email address, normalized to `email:<lowercase address>`; areas use the usual consult grammar. Claims are nonempty paraphrases of at most 16 words, refusing quotation marks (`"`, `“`, `”`, `‘`, `’`), backticks, email addresses, runs of five or more digits, URLs and the field separator ` · `. Links are required, single-line and without brackets. Exactly one of `--reviews`, `--mail` and `--claims` is required; claims dry-run writes nothing, and reruns skip exact existing evidence. An explicit `- **Email:** <address>` person-profile line joins lowercased email evidence to the same canonical id as consults, retaining `via` on candidates. Mail is stored only as derived claims and links, never content or patient, customer or private details.

`brain consult ask --to PERSON --why TEXT --ask TEXT --default TEXT [--area A] [--task T-nnn] [--restricted] [--not-covered TEXT]` can ask any `<platform>:<id>`, even without Owners.md. Read the area's record first; consult only on a consequential choice the record does not answer. Without --area the best word match is used, else general. Ask names the subject and choice in at most 16 words; default and why are required, at most 40 words each. Why explains choosing this colleague and is shown as detail in Needs you. A named task must be open. An identical open area/question returns its existing id. `<agent_dir>/Consults.md` keeps `## Open` and `## Went ahead`, with indented id, to, asked, until, tried, restricted, default and why fields. Waits count 09:00–17:00 Monday–Friday in the configured timezone, beginning at the next opening outside those hours. `brain consult list [--json] [--for PERSON]` lists both sections.

Restricted actions are the one routing gate. Pass --restricted when the answer would authorize production, money or another restricted action; an area listed as `- area` under Owners.md's optional `## Restricted` also sets the flag. The recipient and answerer must be that area's owner, backup or a recorded delegate. `brain consult delegate --area A --to PERSON --by PERSON --words TEXT` requires an owner or backup as --by and records their exact words under `## Delegated`: `- date · Name · to PERSON · words`. Redirects from an eligible answerer can delegate for that consult alone, with an indented `consult: ID · for: question`; this does not authorize another consult. No map or delegate means a restricted consult is refused, naming who may answer if known.

`brain consult answer ID_OR_TEXT --outcome changed|confirmed|redirected --answer TEXT --by PERSON [--to PERSON]` records only the person's exact words. Changed/confirmed answers become `## Decisions` lines: `- date · Name · answer · [[source]] · id:ID` (source optional), with indented `asked: question`. Redirected requires --to, moves the same consult to a fresh recipient and wait, extends tried, and logs the redirect words in Answered without filing a decision. `brain consult overrule ID --answer TEXT --by PERSON` lets anyone correct a recorded decision: `  - overruled date by Name: words` sits beside it, with an Answered entry. In an area listed as restricted, an overrule by someone the gate would not admit is recorded the same way, but the task is told to act on it only once a permitted person agrees (rule 6). Answers, redirects and overrules add evidence to an open task and clear Resume. A decision keeps the consult's original id even when it was answered on a later day.

`brain consult lapse [--dry-run]`, run hourly by refresh, tries the top unmuted, untried candidate who passes any restricted gate, at most three people total. The backup competes through its score. After that, or with nobody left, a restricted consult is held: it stays open with the area's owner (or the first recipient), stops lapsing and tells the task the default is not taken. Any other consult takes the stated default, leaves a Went ahead confirm for the area's owner or the first recipient without one, logs unanswered against the last recipient, writes task evidence and clears Resume. Repeated lapse is idempotent. Writers hold the vault lock. Refresh stages the agent's consult records and affected tasks only when lapse printed an action. Seeders can call `consults.add_evidence(config, area, day, person, kind, text, link="")` to append a deduplicated `## Evidence` line: `- YYYY-MM-DD · platform:id · approved|reviewed|changed|deferred-to · text · [[link or url]]` (link optional).

Needs you and state export use `origin: consult`, Open as ask and Went ahead as confirm, `owner` as the current recipient, `context`/`area` as the area, with default and why/detail included. IDs survive moves and go-ahead; asking again after resolution gets a new id. Asks rank with blocking work and ordinary retirement, stale and overflow actions ignore them. Went ahead confirms expire after five days in nightly; dismissing one removes it. Dismissing an open consult with no takes its default, except a restricted one, which closes without it; stop-asking also records `date · person · stop-asking` under `## Not asked`. Future asks to that person in that area refuse and suggest an unmuted candidate. Done is refused for open consults; resolve directs the caller to consult answer.

`brain consult stats [--json]` counts logged recipient outcomes per area and person: asked, changed, confirmed, redirected, overruled, unanswered, changed share among decisions and median wall-clock hours to an answer (redirects included; unanswered and overrules excluded). Asked counts changed/confirmed/redirected/unanswered entries; open recipient turns are not counted. The weekly series, oldest first by ISO week, counts distinct finalized consults and how many were redirected at least once, even in an earlier week; the rate measures routing corrections. Overrules do not add resolutions. These numbers teach the intellect to ask less where answers confirm its direction and to route better as the record grows.

## Audit

`brain audit [--days 14] [--json] [--sessions-dir <dir>]` is the process view a maintainer can always see: notes by kind with word totals, each folder under the agent directory with its file and dated-file counts (a folder of dated files is the file-per-run smell), monthly ledgers with rows and mean words per row (a ledger of 120-word rows is writing disclaimers, not receipts), recent episodes with their mean size and how many exceed 1500 words, the directory's number of most active notes and their body-word total, and the compiled context word count, which day routines differ from the package defaults, each cron job's runs in the window with mean messages, tool calls, tokens, minutes and end reasons from the session store's own counters, and commits by type. Everything in it is a count, a size or a routine name; no note contents, titles or paths of knowledge notes. Ledger paths are process records and do appear. Finding routines that spend 60 tool calls to find nothing, or ledgers that grow by essays, starts here.

## Health

`brain health` prints an operational report built only from commits, engine state files and counts: the last run of each night stage with ok, stale or never (a stage is ok when its commit covers yesterday or later), installed against recorded engine version and any pending migration, yesterday's digest coverage line, validation problems, note counts by tier, open tasks, and the working tree against origin. `--json` gives the same as data; `--write` saves the committed copy to `<runtime_dir>/health.md` (without the working-tree line, so hourly refreshes only commit real change). The refresh script writes it every hour. An agent asked "how are you" by a maintainer answers from this report; nothing in it is a note's contents.

The validation problem count in `brain health` covers structure and the hygiene checks (Needs you duplicates and machinery, Ask and Why lines, the Primed cap, the channel registry). Work-reference warnings are advisory and excluded from that count. The nightly gates its commit on structure only, and adds a `checks:` line to its report when hygiene problems remain; the evening routine runs `brain validate` and fixes the Needs you ones. One hygiene check keeps CURRENT current: an item whose newest date is more than two weeks old is named (not Needs you, sections titled History or Superseded, or the generated active threads), and Sleep 1 moves it to its note's History, moves a standing direction to its owning note, or rewrites what still holds with today's date. Another names a task that CURRENT or Primed still presents as live when the task's own record says it is completed or cancelled (outside History sections, comments and the generated active threads, and unless the line itself says it is done); Sleep 1 corrects or drops the line.

## Work snapshot

`brain state --json [--vault PATH]` prints a read-only snapshot of the brain's work: schema and engine versions, the vault's short Git HEAD (with `+dirty` for uncommitted changes, or null outside Git), tasks, hubs, routines, triggers, the last 30 days of ledger rows including today, needs-you items, the single shown `idea` (or null), `ideasOpen` (including snoozed ideas), and drafts/reflections. Without `--json`, it prints one line of counts. It writes nothing and has no dependency on its consumers, including Demiurge.

Each task row preserves `"resume": "computer"` unchanged (or its date value, or null). The top-level `"waitingOnComputer": ["T-001", "T-002"]` lists open tasks with that Resume in task-row order, including archived entries; it is `[]` when none. It follows the same visibility exclusions as the task rows and does not require a handoff.

Schema 1 uses deterministic ordering and no generation timestamp, so unchanged vault state produces identical JSON on the same configured date. Fields are only added within a schema version; anything else bumps schema. Tasks retain one identity per ID, with register entries taking precedence over archived copies. Routine names use the latest ledger spelling, falling back to the responsibility hub's records value.

The additive `responsibilities` list comes from hubs and the declared schedule, including routines that have never run. Each row is `{"id": "chicken-alerts", "title": "Chicken alerts", "hub": "Chicken alerts.md", "skill": "nameless-chicken-alerts", "records": "chicken-alerts", "routines": ["chicken-alerts"], "needs": [], "work": null, "delivers": null}`. Hubs retain their existing shape. Existing ledger-based `routines` rows gain `responsibility: "<id>" | null` only when that routine's name maps through the schedule; their other fields and membership stay unchanged. Responsibilities follow the same visibility exclusions as hubs.

Hubs and outputs exclude the configured sources directory, the human profile's folder, people and agents directories, the runtime directory, notes with `tier: private`, and notes with `kind: conversation`. These exclusions also apply to ledger discovery, needs-you source pointers, and ideas, so private proposals cannot leak through the owner queues. Resolvable needs-you links become vault-relative source paths, retaining anchors and IDs.

The additive `shareable` object exports audience-filtered hub titles, ledger receipts, and group member platform ids;
see [what each audience may see](access.md#what-each-audience-may-see-brain-state). It never includes person-specific

## Commands

`brain version` prints the installed package version. Without `AGENT_HOME`, `brain paths scripts` and `brain paths records` exit with `AGENT_HOME is not set`; the other paths and `brain validate` remain available.

`brain export-sessions [--date YYYY-MM-DD]` reads harness sessions, archives conversations as `<vault>/Conversations/Sessions/<id>.md` and routines as `$AGENT_HOME/records/sessions/<id>.md`, and copies unchanged source JSON to `records/sessions/jsonl/<id>.json`. Only changed content is rewritten. A date selects sessions started or active that day; omitting it exports all sessions. `brain paths records` prints the records root.

**Session kinds.**** Every exported session is classified as a conversation, a routine (a run whose `speaker.platform` is `cron`), or an evaluation (session id matches `Evaluation fixture`, `retrieval check` or `RC-nn`, or the first user message begins `Evaluation fixture:`). The digest includes only conversations unless `--include-routines` is passed; attribution ignores evaluation sessions entirely and takes only explicit citations, never observed opens, from routines. Paths under `<agent_dir>/Retrieval Checks/` never earn observed credit. The digest's `coverage:` line reports how many sessions of each kind were included or excluded and how many turns the word cap omitted.

`brain migrate-check` and `brain migrate-done` carry the agent's part of an upgrade: the package ships a Markdown prompt per version that needs one (see `src/brain/migrations/README.md`), `migrate-check` writes the applicable ones to `<runtime_dir>/pending-migration.md` after each nightly update and, when that file is new or changed, declares a one-shot `brain-migration-<version>` routine two minutes out in the schedule so it starts at once, the recall skill makes the agent perform them, and `migrate-done` records the version. `<runtime_dir>/engine-version` is the recorded version, committed with the vault; a vault without one is new, so `migrate-check` records the installed version and queues nothing. `brain migrate-done --defer "<step>"` (repeatable) closes a migration while carrying a step the agent may not do unattended, such as an edit to a protected file, for a maintainer in `<runtime_dir>/deferred-steps.md`: a maintainer's sessions are told how many wait, `brain health` counts them, and the owner's Needs you never carries machinery; a step that waits on a future event belongs in Triggers. `brain health` dates a pending migration from the commit that added the current file.

`brain update` upgrades the package from `update_source` using the interpreter that owns `brain`, then reinstalls the scripts atomically per file. Without `AGENT_HOME`, the package still updates and it prints `scripts not reinstalled: AGENT_HOME is not set`. The export script runs it first every night, so a vault stays current without anyone touching the machine; a failed update is reported and the archive continues on the installed version. `brain paths python` prints that interpreter.

### Session archives

Digest and attribution read the harness session JSON shards under `$AGENT_HOME/records/sessions/jsonl/`, using the schema in [runtime.md section 4](runtime.md#4-what-the-runtime-records-and-the-engine-reads). Without shards they still read archived Markdown, including transcripts already in older vaults. Without a configured runtime they use the vault's `Conversations/Sessions/`.

The Markdown parser is line-based, not a Markdown AST. Case-insensitive role markers include headings such as `## assistant` or `### Assistant`, bold names such as `**assistant**`, `assistant:`, and metadata such as `role: assistant` (also quoted or list-prefixed). The same forms recognize user/human, system, developer, tool and function roles; only the nearest preceding assistant marker permits a line whose first non-whitespace text is `Sources:`. If there are no recognized role markers anywhere in the file, all such Sources lines qualify. Sources text uses the existing explicit-use parser, including its orientation-note exclusion; surrounding prose is not inferred as reliance, and fenced examples are not specially interpreted.

Each row takes the nearest preceding valid ISO-8601 date-time in the file (minutes required, optional seconds/fraction/zone), otherwise the first valid YYYY-MM-DD in the filename, then the nearest dated parent directory, then the file's local mtime date. A date-time inside the Sources line itself is not preceding that line. The reason is `cited in session <file stem>`; rows are deduplicated within the export batch and against the relevant monthly Use Log by `(date, target, reason)`, regardless of timestamp time or source type. Re-exporting the same session stem is safe; renaming stems changes attribution identity. Review a report-only attribution against a real export before relying on a new export layout.

JSON attribution reads `entries[].at`, `item.role` and `item.text`. Assistant `Sources:` lines retain explicit parsing and `(date, target, reason)` deduplication, with reason `cited in session <id>`. Observed rows use `opened on demand in session <id>` and deduplicate by `(date, target, source=observed)` across sessions and monthly logs.

Observed attribution excludes `vault.ORIENTATION`, every note selected for the directory's active block when the directory section is enabled, and all paths under Conversations, agent/Dreams, agent/Explorations, agent/Use Log, agent/Sleep Log and agent/Tasks Archive. Loading is not use: automatic context and bookkeeping reads must not reinforce themselves just by being loaded.

Only `item.type = "tool_call"` supplies observed paths, from `item.arguments` (JSON text) and `item.name`. Paths use the configured vault prefix, accept spaces and end at `.md`. Only existing vault notes receive observed rows; tool results and reasoning never count. An observed row records an open, not semantic reliance.

For a named `terminal` call containing `brain retrieve`, shell quoting is parsed with `shlex` and the positional query is recorded instead of any reads from that call; `--vault`, `--limit`, their `=value` forms and `--json` are skipped. This is not a shell interpreter: malformed quoting yields an empty query, and dynamic shell expansion or unrecognized export argument fields are not reconstructed.

### Digest

`digest` is a separate command, not another step inside `nightly`. The default sessions directory is `$AGENT_HOME/records/sessions`, this profile's own export; until that folder exists, an existing `<vault>/Conversations/Sessions` is read instead so an older export script keeps working. It reads the harness shards, falling back to archived Markdown when none exist. Without `--write`, only the complete digest is printed to stdout. With `--write`, only the digest file is saved, and its path and retained conversation word count are printed. It never attributes uses, changes notes, or publishes anything.

The harness schema is explicit: `id`, `speaker.platform`, and timed `entries` containing messages, tool calls, tool results or reasoning. Only user and assistant message text enters the digest; `said` preserves what the person typed when the harness added context. Timestamps use the owner's configured zone and filter by day. Tool calls accumulate reads and retrieval queries for the next assistant reply. System context, tool output and reasoning are excluded.

Markdown fallback reuses attribution's role and ISO timestamp recognition (including `human` as user), taking a preamble's first `#` heading as the title or otherwise the filename stem. Role-marker suffixes may carry inline content or timestamps; standalone or labeled timestamps before a turn's text are metadata. Fenced blocks and timestamps inside ordinary message bodies are preserved, not treated as metadata. Files with no recognized roles contribute nothing. When all message timestamps are missing, the filename/dated-parent/local-mtime date fallback is used with an approximate-time note. The parser is line-based; role-like lines outside code fences remain ambiguous, so review a real export before depending on its layout.

Turn labels use `BRAIN_HUMAN_NAME` (default `Human`) and `BRAIN_AGENT_NAME` (default `Agent`), resolved once when the script starts. These environment variables affect display labels only, not paths or export role parsing.

After each assistant turn's original text, `reads: <paths>` lists distinct tool-call note paths in encounter order since the preceding text-bearing assistant turn in that session; textless tool-call messages accumulate into the next such turn. Each retrieval adds `retrieve: "<query>"` on its own line, with JSON string escaping; tool results never add reads, and digest reads include automatic notes even though observed attribution excludes them.

Sessions are ordered by their first retained timestamp; turns within each session are chronological, with stable input-order ties. `--max-words` (default 25000, nonnegative) counts whitespace-separated words of retained message text only, excluding frontmatter, headings, turn labels, fallback notes, reads/retrieve annotations and the truncation notice. It selects a chronological prefix across all sessions, stopping before the first whole turn that would exceed the cap, then groups those turns into session sections. The header counts only represented sessions and retained conversation words; a final truncation line counts every remaining turn. The generated date is today's Pacific date: identical inputs on the same generation date produce identical bytes, and unchanged files are not rewritten; regeneration on a later day updates that header date.

## What `nightly` does, in order

**Digest (before the pass).** The nightly export script runs `brain digest --date YYYY-MM-DD --write` after exporting sessions. It then runs `brain redact` over the session transcripts and digests before committing: well-known key shapes (Google, OpenAI, Anthropic, Stripe, Slack, GitHub, AWS, private-key blocks) and values assigned to secret-named variables become `[REDACTED:<kind>]`, so a credential pasted into a conversation is never pushed. Sleep 1 reads `Conversations/Digests/YYYY-MM-DD.md` for consolidation before invoking `nightly`.

1. **Rollover.** Create this month's Use Log, Sleep Log and Tasks Archive files if missing.
2. **Frontmatter defaults.** Every mechanical note gets `kind`, `tier`, `pinned`, `uses`, `uses_inferred`; a new hub, profile, reflection, episode or primed note gets today as its first use. Logs, dreams and daily archives are left alone. Retired generated views are removed before the pass.
3. **Load tasks.** One `Task` per ID. A generated `- **Warm:**` line in the register is replaced by its archive body; a full register entry is canonical over the archive; a duplicate ID keeps its first entry. Archived open tasks the register does not list are loaded too.
4. **Attribute sessions, then fold uses.** When `--sessions-dir` is given, append new assistant Sources citations and harness observed reads to the relevant monthly Use Logs first. Every dated row in `agent/Use Log/*.md` is then credited to its target: explicit rows into `uses`, inferred and observed rows into `uses_inferred` (half weight), task citations into the register comment. An explicit note use supersedes an observed use on the same date, including previously folded observed credit; observed rows never credit tasks, which rely on citations or triggers. Rows are skipped when future-dated, `MISS`, a trigger, `live | unconfirmed`, or aimed at a log, dream or daily archive. Credits are date sets, so folding the same row twice changes nothing.
5. **Activation and tiers.** ACT-R base-level activation from the use dates; hot, warm or cold per the spec. Pinned stays hot, unconsolidated conversation records cannot go cold, an expired Primed note goes cold.
6. **Triggers.** Fire date commitments (a fired commitment adds a use to its task), mention once and then retire intentions whose source went cold.
7. **Write.** Save changed notes' frontmatter over their bodies as they are on disk. Under the vault lock, on a fresh read of the register, place each open task: hot as a full entry bounded to 150 words with older evidence (and every Reviewed line but the newest) archived, warm as one line with the full body in `agent/Tasks Archive/T-nnn.md`, cold as archive only. An open handed-off task (not set aside) is always hot. An entry that cannot be bounded without judgment is left exactly as it is and reported for Sleep 1; the night goes on. A completed or cancelled task leaves the register: its entry to `agent/Tasks Archive/T-nnn.md`, a line to the month's `agent/Tasks Archive/YYYY-MM.md`, and any Needs you ask sourced to it is resolved. All open tasks remain named in the directory, including archived ones. Rebuild CURRENT's active-threads block, raise the once-only Library asks for eligible unopened drafts, and expire confirms and unlinked asks under the vault lock. Give each new portrait claim its id. Remove any retired Hot Set.md and Warm Index.md generated views.
8. **Compile context.** Rebuild the repository-root `.context.md` from the source notes, with the most active notes at the start of its directory, and report its word count (warning, not failure, above 6000 words).
9. **Validate.** Required frontmatter, resolvable wikilinks on changed notes, pinned notes hot, superseded headers present. On failure: print, append a failed entry to the Sleep Log, exit 1, no commit.
10. **Record and publish.** Append the report to the Sleep Log. With `--commit`, stage the configured vault minus legacy `.brain` state plus repository-root `.context.md` and commit as `sleep1(<date>): <summary>`. With `--push`, `git pull --rebase origin main` then push; a conflict aborts the rebase and exits non-zero with nothing pushed.

Without `--write` the same pass runs on a temporary copy of the agent tree and only prints the report.

## Idempotence and interruption

Every step is a function of the files as they are. Running the same date twice produces the same files, apart from a second Sleep Log entry. A run killed halfway leaves some notes saved and others not; the next run converges. Library asks keep their per-work asked dates in runtime records; if an ask was saved before its record write failed, its standing source recovers the record on the next run, before asks lapse. If a run must be undone, `git revert` the commit; Library asked records live outside that history and remain asked.

## What it does not do

Read Gmail or any connector, capture conversations, judge salience or surprise, infer reliance, write facts, or decide anything about the owner. Those are the agent's judgment steps in the routine files. The script is the same every night; the judgment is logged and audited by Sleep 2.

## State

- Note frontmatter: `tier`, `activation`, `uses`, `uses_inferred`, `pinned`, `consolidated`, optional `index_line`.
- Register comments: `<!-- brain: state=ready; uses=...; inferred=...; tier=...; activation=... -->` under each `### T-nnn` heading. `state` is `ready`, `in_progress`, `blocked`, `waiting_for_owner`, `set_aside`, `completed` or `cancelled`; a task is open unless completed or cancelled. `set_aside` is open and recoverable but never in `needs-you`, Sleep 2's nudges or `stale-tasks`. `yours` is the owner's own work: open, never in `needs-you`, never continued as a handoff, listed by `stale-tasks` after 14 quiet days so the evening can ask once whether it is still on, done or dropped. `brain task T-nnn done|drop|yours [--why ...]` changes one task for the owner (completed, cancelled, or yours), with a dated line. Written states are normalised (case, spaces and hyphens; `done` is `completed`; `parked`, `deferred` and `deprioritized` are `set_aside`). Legacy comments without `state` keep their meaning: only `status=open`, or no status, is open. `state` wins over `status`, which is dropped on rendering; the engine never invents a missing state. `brain validate` reports an unknown state; the nightly never gates on one, so a mistyped state cannot stop the night's commit.
- Task fields: `- **Status:**` keeps the human-readable detail; optional `- **Hub:** [[Target]]` names the hub the task serves. Labels and anchors are allowed (`[[Target|label]]`, `[[Target#anchor]]`); the hub is `Target`.
- Legacy `.brain/state.json` (not managed or required by the package): only `channels`, the Gmail acknowledged-coverage checkpoints described in [[memory/agent/Channels|Channels]]. The agent maintains it; the script never reads or writes it.
