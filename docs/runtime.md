# The runtime contract

What agent-brain needs from whatever runs the agent, and what it gives back. The Demiurge harness (`demiurge/apps/harness`) is the runtime. Nothing in the engine may assume more about its runtime than this page says. When the contract changes, this page changes first, in the same release, and the change is named in `CHANGELOG`-style prose at the end.

## 1. Who owns what

| | Owned and written by | Read by |
| --- | --- | --- |
| The vault (notes, skills, SOUL, the schedule) | the engine and the agent | the runtime, read-only, except the files the agent writes through its tools |
| `<vault folder>/<runtime_dir>/schedule.toml` (beside `engine-version`), the declared routines | the engine (`brain schedule`), the agent through that command | the runtime |
| `<vault repo>/.context.md`, the compiled session context | the engine (`brain compile-context --write`) | the runtime |
| `$AGENT_HOME/records/`, routine and engine state (except `works/state.json` below) | the engine and the agent | the engine |
| `$AGENT_HOME/harness/`, run state: jobs, runs, sessions | the runtime | the engine, read-only |
| `$AGENT_HOME/works/LIBRARY.md`, available works and notices | the runtime | the engine, read-only |
| `$AGENT_HOME/records/works/state.json`, work sync state | the runtime | the engine, read-only |

`<runtime_dir>` is `brain.toml`'s `runtime_dir`, default `Runtime`. This folder holds the schedule, skills and engine state; `.context.md` lives at the vault repository root.

## 2. Environment

Every process the runtime starts for an agent (its shell, a routine's script, a brain call) gets:

- `VAULT_REPO`: the vault's git repository, also the working directory.
- `AGENT_HOME`: the agent's workspace root, where `records/`, `harness/` and `works/` live. The engine reads only `AGENT_HOME`. Without it, runtime-dependent paths report `AGENT_HOME is not set`; `brain version`, vault paths and `brain validate` still work. `brain update` installs the package and prints `scripts not reinstalled: AGENT_HOME is not set`.
- A `PATH` holding `brain` and `demiurge`.

The harness sets `BRAIN_RUN=routine` for routine runs and `BRAIN_RUN=worker` for worker runs. Conversation shells leave it unset and may set `DEMIURGE_CONVERSATION` to their conversation id. Task workers also set `DEMIURGE_TASK` (and may set the thread's conversation id). `DEMIURGE_TASK` and `BRAIN_SPEAKER` on `cron` or `subagent` independently identify a routine or worker. With none of these signals, the session is a conversation, including when `AGENT_HOME` is set. In personal vaults, new tasks and ideas in routine or worker runs need `--goal G-n` naming an active goal, or `--source` containing the owner's actual quoted request. A follow-up to the worker's current task is asked work; it inherits the parent's goal only while that goal is active. An enterprise vault follows its assigned duties and initiatives.

No credential is ever in this environment beyond what `agents/<id>.json`'s `env` names for that agent.

## 3. The schedule: declared by the vault

`<vault folder>/<runtime_dir>/schedule.toml` (beside `engine-version`) is the single source of truth for which routines an agent has and how each runs. The runtime reconciles its jobs to it; it never edits the file. The agent never edits the runtime's job store; it changes a routine with `brain schedule`, which edits this file and validates it.

```toml
# The routines this agent runs. Edit with `brain schedule`; the runtime applies changes within a minute.

[routines.watch]
cron = "*/15 6-22 * * *"        # five-field cron, in the owner's zone (`brain timezone`)
skills = ["tars-watch"]
prompt = "Run watch."
deliver = "demiurge"            # "local" (default), "demiurge" (the owner's Home), or "demiurge:<conversation id>"
monitor = "watch-signal.sh"     # optional; see below

[routines.demiurge-sync]
every = "15m"                   # instead of cron: "<n>m" or "<n>h"
script = "demiurge-sync.sh"
agent = false                   # a script only, no model run

[routines.career-questions]
at = "2026-11-05T06:30:00-05:00"   # instead of cron: once
skills = ["tars-recall"]
prompt = "Send Rohan the morning questions."
owner = true                    # asked for by the owner by name; only they change or remove it
```

Fields, per routine (the table name is the routine's name, `[a-z0-9-]+`, unique):

| Field | Meaning |
| --- | --- |
| `cron`, `every`, `at`, `after` | exactly one: when it runs. `after = "<routine>"` runs it when that routine finishes |
| `skills` | skills loaded for the run, by name, from `brain paths skills` or the agent's own skills folder |
| `prompt` | the run's instruction; default `Run <name>.` |
| `deliver` | where the run's final response goes, default `local` (nowhere) |
| `monitor` | a script under `$AGENT_HOME/scripts/`; the run happens only when its stdout changed since the last run that happened |
| `script` | a script under `$AGENT_HOME/scripts/` run before the agent, its stdout given to the run; with `agent = false`, the whole job |
| `agent` | default `true` |
| `workdir` | default `$VAULT_REPO` |
| `enabled` | default `true`; `false` keeps the routine declared but paused |
| `owner` | default `false`; `true` marks a routine the owner asked for by name |
| `responsibility` | optional responsibility id, matching `^[a-z0-9][a-z0-9-]{0,62}$`; explicitly assigns the routine to that hub; unknown ids are validation warnings |
| `needs` | default `[]`; `["computer"]` means the work needs the owner's computer (the harness's hands target); only `computer` is supported |

Set these with `brain schedule set <name> --responsibility <id> --needs computer`; clear them with `--responsibility "" --needs ""`, like clearing `--skills`. `brain schedule list --json` maps each routine name to every field, both of these included (`null` and `[]` when absent), with `prompt` resolved (`Run <name>.` when unset); the runtime reads the schedule through it rather than parsing the file. `set` refuses unknown needs; `brain validate` warns about them in a hand-edited file without failing validation. Responsibility ids and fallback links are described in [the engine guide](engine.md#responsibilities).

Reconciliation, by the runtime, at start and whenever the file's modification time or size changes (checked each scheduler tick):

- A routine in the file and not in the runtime's store is created. One in the store and not in the file is removed. One in both takes the file's definition and keeps its run state (last run, next run, the monitor's last hash, failure streak).
- An invalid file changes nothing: the runtime keeps the last valid set, logs `schedule: invalid <path>: <reason>; keeping jobs`, and the engine's `brain validate` names the problem. A valid but empty file removes every job.
- An `after` routine runs once each time the routine it names finishes, whether it succeeded, failed or skipped, and never on a clock of its own. A routine cut off by a restart has not finished: it runs again when the runtime is back, and its successor follows that run. A paused successor is skipped and the chain stops there. Every chain starts from a routine with `cron`, `every` or `at`; a chain that leads back on itself, or names a routine that is not declared, is invalid. The night is built this way (see `docs/night.md` in demiurge).
- A one-shot (`at`) routine that already ran stays done even if its time is edited; declare a new name to run it again.
- The runtime records each job's state as in section 4, keyed by the routine's name.

Monitors: the runtime runs the monitor with the routine's environment and working directory, hashes its exact stdout, and skips the run when the hash equals the last one that led to a run. A monitor that exits non-zero is a failed run, never a change, and leaves the stored hash alone. When it does run, the monitor's stdout is given to the run as context.

Handed-off tasks run through background workers, outside the routine schedule. The runtime reads `brain continue --due --json` and starts one chunk of one task with "Run continue for T-nnn.". The default due list combines regular tasks within budget and daily tasks from 12:00 in the owner's timezone with `chunksToday == 0`, preserving each row's `pace` and ordering both paces least recently worked first. State, Delivers, Resume (including a later time or a computer rest) and review-cap gates still apply. A counted chunk removes a daily task from that list for the rest of the local day; regular work continues while due. The runtime keeps one worker per task and counts each finished run with `brain continue --chunk T-nnn --run <run id> --text "<final reply>"`, saving the reply as the checkpoint; the engine's daily budget is the only daily cap. Text `--due` uses the same selection. The default schedule has no `continue` or `continue-daily` routine, and validate and health require no continue heartbeat.

## 4. What the runtime records, and the engine reads

`$AGENT_HOME/records/continue/tasks/<id>.json`: the engine's per-task checkpoint, `{task, at, text}`, atomically replaced by `brain continue --checkpoint T-nnn --text "..."`. Both text and JSON due lists expose its text. The legacy `records/continue/state.json` is left untouched. `records/continue/progress.json` remains keyed by resolved vault path and task id; each record adds `chunks: {date, count}` for the owner's local day. Missing counts mean zero.

`$AGENT_HOME/works/LIBRARY.md`: a `# Library` heading, then one line per work, `- Title | slug | form | status | editable|read-only | ISO updated`, followed by plain-sentence notices about refusals, conflicts or errors. Each work is a git repository with a working copy at `$AGENT_HOME/works/<slug>/`. The runtime refreshes the listing on every run. The engine's `library` context section strips the title, includes up to forty work lines and keeps every notice; it is silently absent without `AGENT_HOME`, the file, or any works or notices.

`$AGENT_HOME/records/works/state.json`: a map from work slug to `{lastPull?, lastPush?, lastCommit?: {hash, when}, refusal?, conflict?, error?}`, with ISO timestamps. `_library` is reserved, not a work. The runtime writes it; the engine reads successful pushes as progress for a task naming that work. A local commit without a push does not count, and missing or unreadable state is no progress.

`$AGENT_HOME/harness/jobs.json`: a JSON array of jobs (a reader also accepts `{"jobs": [...]}`), each job `{id, name, schedule, skills, prompt, script?, noAgent?, monitorScript?, monitorHash?, deliver, workdir?, enabled, nextRunAt?, lastRunAt?, lastStatus?: "ok" | "failed" | "skipped", lastError?, failureStreak?}`. The engine reads it through `brain.runtime.jobs()` and nowhere else.

`$AGENT_HOME/harness/runs/<YYYY-MM-DD>.jsonl`: one line per routine run, in the file for the UTC day it started, `{id, jobId, status: "completed" | "failed", startedAt, finishedAt?, outcome?: "delivered" | "silent" | "skipped" | "local", error?, outage?, sessionId?, result?}`. Worker chunks are logged the same way in `harness/worker-runs/<YYYY-MM-DD>.jsonl`. Before demiurge #453 both were single files, `runs.jsonl` and `worker-runs.jsonl`, which the harness splits into the daily files once and renames to `.migrated`.

`$AGENT_HOME/harness/sessions/<YYYY-MM-DD>/<session id>.json`, one per conversation or routine run:

```text
{ id, day, speaker: {platform, userId?, userIdAlt?, userName?, chatId?}, startedAt, timezone, system, sessionBlock,
  owner: bool, peopleSeen: [...], entries: [{at, item, said?}], recorded: int, usage: {...} }
```

`item` is one of `{type: "message", role: "user" | "assistant", text}`, `{type: "tool_call", id, name, arguments}`, `{type: "tool_result", callId, output}`, `{type: "reasoning", ...}`. `speaker.platform` is `cron` for a routine run. `said` is what the person typed when `text` carries added context. The night's digest and attribution read these files directly.

## 5. What the runtime calls

At the start of a conversation, in parallel: `brain paths soul`, `brain paths skills`, the cached `.context.md` (running `brain compile-context --write` if absent; a routine whose skill declares its sections gets `brain compile-context --sections <list>` instead, see below), `brain timezone`, and `brain session-context --json --platform --user-id [--user-id-alt] [--user-name] [--chat-id] [--ack-notices]`, which prints `{block, owner, member, answering}`. App goal writes refresh the cache; per-session app notices come through session-context. Without `--ack-notices`, session-context is read-only, including repeated previews of pending notices.

Personal owner sessions put message defaults before profile background, then end the owner card with Working together, explicitly binding every reply over message and skill defaults. Routine owner cards use the same framing. Its existing 250-word allowance is reserved before background is cut to the shared 450-word budget.

`brain tellable <person|known|anyone> [--json]` resolves the owner's tellable note for an audience; JSON is `{person, groups, subjects: {subject: {level, lines}}}`. Outside sessions (including intellects, resolved for their owners) carry those lines under `What you may tell <name> about <owner>, and nothing else:`, the format in `brain.session_context.TELLABLE_HEADING`, and session-context's `answering` is true for them. The runtime keys on `answering` (the current harness falls back to matching the heading when an older engine omits it): such a session gets only its session context, no compiled context, prefetched notes or vault tools (`read_file`, `search_files`, `terminal`, `write_file`, `patch`). Tools that reach the owner remain available. The resolved lines are capped at 600 words, dropping oldest evidence first, and say `Nothing.` when empty. Owner, enterprise member and routine sessions have no such block; enterprise intellect sessions do. Legacy and missing disclosure notes still produce the block, resolved as `anyone`.

Before each owner message: `brain prefetch --json [--owner] [--seen NAME ...] -- <message>`, which applies `[context]` and its `BRAIN_*` overrides and prints `{text, people}`: `text` is the block to put before the message (the people it names, in the owner's own sessions and only those not in `--seen`, then the matching vault notes), and `people` every person it names, for the runtime to add to the session's `peopleSeen`.

The schedule is read with `brain schedule list --json` (section 3); the current harness still resolves `brain paths schedule` and parses the file itself.

After a conversation goes quiet: `brain record-spec --json` (the record call's system prompt, instructions, JSON schema, transcript cap and `held`, the open asks, loops and tasks to append to the conversation instructions), then the model call, then `brain journal append [--platform] [--user-id] [--user-id-alt] [--session <conversation id>]` with the record on stdin (an ask the record raises names that conversation; the default is `DEMIURGE_CONVERSATION`) (a record of `nothing` that captures nothing is skipped), and `brain ledger append --json` after a routine. A reply that is not a valid record is no record.

Background workers (section 3): `brain continue --due --json` for what to start; `brain continue --engaged T-nnn [--by <platform>:<id>] [--instruction TEXT]` when the owner writes in a task's thread; `brain continue --review-context T-nnn --json` and `brain continue --review T-nnn --verdict converging|met|circling|stuck --reason TEXT [--ask TEXT]` for a direction review; `brain continue --wake computer` when the owner's computer reconnects, ending rests on it. The worker's own run counts its chunk and writes its checkpoint through the continue skill.

From the owner's app, as control messages the runtime turns into argv without a model turn: `brain needs-you --dismiss <id> --reason no|stop-asking`, `brain task <id> drop|done --by-owner`, `brain ideas --respond <id> --answer yes|not-now|no|stop-asking`, `brain consult answer <id> --outcome <outcome> --answer TEXT --by <platform>:<id>`, `brain portrait mark <id> right|wrong|not-this [--words=TEXT]` and `brain portrait seed --account <address> --hand-off`. `brain state --json` feeds the push. `brain state --stamp` prints a cheap fingerprint of everything the export reads (file paths, sizes and times, runtime records, engine version, HEAD, the owner's day), so a runtime can export again only when it changes; the current harness instead fingerprints the agent and vault folders it finds through `brain paths soul` and `brain paths vault`. An answering session without a way to reach the owner gets an `ask_owner` tool that runs `brain needs-you --ask TEXT [--why TEXT]`.

Goal controls run argv arrays: `brain goals new <title> --words <words> [--reach [--by YYYY-MM-DD]] --from-app`; `brain goals G-n edit [--title …] [--words …] [--by YYYY-MM-DD | --clear-by] --from-app`; `brain goals G-n reached|set-aside|reopen --why <why> --from-app`. App edits refresh the cached active goals immediately. The engine records the app change until the next owner/routine `session-context --ack-notices` or printed CLI context including goals; cached context writes, nightly refreshes and state exports never consume it. Transient notices stay out of `.context.md`, since the harness may reuse that file between sessions. The context says once "<person> added/changed this in the app: …". `<runtime_dir>/goals.json` is engine-owned capture and pending-notice state, shared under the vault lock. The current app controls are `brain goals G-n keep --from-app`, `brain goals G-n not-a-goal [--why …] --from-app`, and `brain goals G-n to-task --from-app`. These controls and non-inferred `new` require `--from-app` or `BRAIN_SPEAKER=<platform>:<owner-id>` identifying the owner (including `cli:<id>` for the local owner). Keep adopts a reading; not-a-goal and to-task archive and refuse it, detaching linked open tasks. To-task ends with `G-n · became T-nnn` for the app to parse. An owner edit or reopen adopts an inferred goal as said.

### A routine's context

A routine's skill may declare, in its frontmatter's `metadata.runtime`, the compiled-context sections its run needs: `context: [start, current, tasks, library]`, from `before`, `start`, `current`, `primed`, `goals`, `triggers`, `upcoming`, `tasks`, `library`, `directory`. The runtime then loads `brain compile-context --sections <those>` for that run instead of the whole `.context.md`; an empty list means no compiled context. A skill without the declaration gets the whole context. The engine owns these declarations, since it owns the routines; a vault's own skills may declare them too. Requested sections remain within the vault's `[context].sections` allowlist; an explicit list must include `library` to load it.
